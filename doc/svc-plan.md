## 2b. ここからの計画

**2026-09-15 更新（①と③の 1 を実施した後）。** 直列経路は M5 で一旦終わり、M6 は
**起動条件つきに降格**しました（must ではありません。[起動条件](#m6-streaming-student)）。
**ここから先はすべて品質を上げる作業です。**

### 分かっていること（すべて確認済み）

| 軸 | 状態 | 出典 |
|---|---|---|
| **同一性（話者類似度）** | **Seed-VC と同等**（0.5899 対 0.5912）。**主観でも判別できない** | M5 訂正後 / ① |
| **音程・timing** | **LeapSVC が上**（F0 相関 0.9996 対 0.9978 / V/UV 99.2% 対 98.7% / timing 73.9% 対 70.8%） | M5 |
| **信号品質** | ほぼ上限（上限との差 −0.008〜−0.026） | M5 / GAN |
| **明るさ** | target 本人 1160 Hz に対し LeapSVC 1067 Hz（Seed-VC 2149 Hz）。**target 忠実を採ると決定** | 2026-09-13 |
| **選好** | **Seed-VC が上**（25 判定中 21。side の偏りは無く、系の判断として成立）。差は明るさで説明が付く | M5 blind |
| **明瞭度** | **日本語 +5 点前後 / 英語 +10〜19 点**（n=4〜6）。**系間比較はまだできない** | ③ の 1 |
| **速度** | GPU 合計 RTF 0.464、**うちボコーダー 93%** | M5 |

### 止まった理由は、2 つとも測定側だった

**①も③も、品質の話で止まったのではなく測り方で止まりました。**

| 何が足りないか | 症状 |
|---|---|
| **上限を run ごとに作り直している** | 同じ V3 で 26 clip 中 **6 本の上限 CER が 5 点超ずれた**（最大 88 点）。**CER の系間比較が成立しません** |
| **主観テストに anchor が無い** | **「2 系が同一」と「評価者が判別できていない」を区別できません** |
| **日本語の未知 source が無い** | 明瞭度を読めるのは日本語と英語だけで、**日本語は hold-out 6 本（= target 本人）のみ** |

**したがって、先に測れるようにします。** 安く、後続のすべての判断に効きます。

### 計画

| 段 | 作業 | 何に答えるか | 費用 |
|---|---|---|---|
| ~~1a~~ **実施済** | 上限を 1 度だけ作って共有する（`--ceiling-from`）+ `convert.json` に記録 | **済**（2026-09-15）。原因は CUDA ではなく**ボコーダーの乱数**だった | 済 |

| **3b** | 特徴抽出前の pitch augmentation | F0 → スペクトル傾斜の結合をモデル側で緩める | 前処理の作り直し + base 再学習 |

**推奨: 1a → 2a。**

**2a を推す理由（③ の 1 で出た新しい根拠）:** **明瞭度が崩れるのは男声 +12 半音の clip** です。
英語 6 本のうち男声 2 本が **+16.0 と +100.0 点**（ASR が文ごと作り直すほど）で、女声 4 本は
**+0.0〜+20.3 点**でした。**いま全部の男声に +12 を渡していますが、根拠は「+7〜+12」という
範囲だけで掃引していません。** `num_steps` を 16 に決めたのと同じ形で、**再学習なしに既定を
決め直せます。**

**1a を先にする理由:** 2a は明瞭度で判定します。**上限が run ごとに動く状態では、掃引の差と
測定のノイズを区別できません**（実測で最大 88 点動いた）。

**3a（案 B）の期待値は下がりました。** 主要判定に据えた話者類似度が**すでに Seed-VC と同等**で、
**主観では判別できない**ためです（①）。target 自身の上限に向けた余地（回復率 75.3%）は残りますが、
**詰めても聴いて分かるとは限らない**という証拠が出ています。**捨てはしませんが、2a より後です。**

**やらないと決めたこと:** 出力の明るさを上げること（2026-09-13 決定）。選好は取れますが
**target から離れます**。

### ①【実施済 2026-09-15】target 類似の blind

**これは preference test のやり直しではありません。質問が違います。**

**質問そのものは最初から登録されていました。** [評価計画](svc-evaluation.md) 5 節の
blind test の質問 1 が「どちらが target singer に似ているか」です。**実施したのは 3（自然さ）と
5（総合）だけ**でした。

**質問 1 を外した根拠は、後に測定誤りと分かった数値でした。** `out/m5/blind/README.md` には
「話者類似度は既に客観指標で測ってあります（LeapSVC **0.4981** / Seed-VC 0.5912）」と書いて
外しています。**この 0.4981 は上限の混入による誤り**で、訂正後は **0.5899 対 0.5912**、
つまり**ほぼ同等**でした。**「測ってあるから聴かなくてよい」の前提が崩れています。**

| | preference（実施済み） | **類似（提案）** |
|---|---|---|
| 質問 | どちらが良いか | **どちらが target 本人に似ているか** |
| target 本人の録音 | 参考として添えた | **判断の基準。必須** |
| 結果 | Seed-VC 選好（25 判定中 21） | 未実施 |

**材料はそろっています。** `out/m5/blind/paired/`（RMS を揃えたペア）と `context/`
（target 本人の録音と、両系で同一の変換元）をそのまま使えます。**上限
（`*_vocoder_only.wav`）は参照にできません** — LeapSVC 自身のボコーダーの出力なので、
耳が癖を覚えると A / B を当てられます。

**登録すること:** 質問文、参照の与え方、clip 数、tie の扱い、そして**何が言えるか**。
**preference の結果は取り下げません。** 別の軸を足すだけです。

**注意（主張の範囲）:** 類似で勝っても **「Seed-VC より良い」とは書けません**。この表現は
preference を含む判定に予約されています（[主張ルール](svc-prior-art-license.md) 6 節）。
書けるのは**「target への類似では同等（または上回る）」**という、**軸を明示した記述**だけです。

#### ①の事前登録（2026-09-14 決定。**聴く前に書いた**）

上限は **GT mel をボコーダーに通した再合成**で、**checkpoint に依存しない量**です。ところが
**同じ V3 ボコーダー**の 2 つの run で上限 CER を突き合わせると:

| | |
|---|---:|
| 完全一致 | **19 / 26** |

**原因（2026-09-15 に特定。当初の見立ては誤りでした）:** **NHVSing の ONNX に
`seed` 属性の無い `RandomNormalLike` があります**（node `node_randn_like`、属性は `scale` と
`mean` だけ）。**ボコーダーが自分でノイズを生成しており、ONNX Runtime は毎回別の乱数を
引きます。** したがって**ボコーダーを通した出力は run ごとに必ず変わります** ―― 上限も
変換結果もです。

~~GT mel を CUDA で作り直しているため~~ という見立ては**誤りでした**。**CPU +
`torch.use_deterministic_algorithms(True)` の 2 回の run でも上限の sha256 が一致しません**
（実測。`out/repro/r1` 対 `r2`）。**device も決定的モードも関係ありません。**

**ASR は離散で不連続なので、わずかな音の差が書き起こしを丸ごと別物にします。** 連続量
（SQUIM・spectral centroid）にはこの感度はありません ―― **CER に強く出る問題**です。

**訂正:** この作業の途中で「V3.1 は上限の書き起こしがより安定する」と書きましたが、
**誤りです。** 同じ V3 の GAN run も日本語の上限中央 1.2% / n=6 で V3.1 と一致しており、
**run 間のノイズ**でした。V3.1 の改善ではありません。

**分かった副産物:** `CUBLAS_WORKSPACE_CONFIG=:4096:8` は**既に module の import 時に

### 1b【実施済 2026-09-15】主観テストに anchor（catch trial）を入れた

**確認済み:** ①で、判定 4 票すべてが「後に聴いた側」に張り付き、評価者は「意味がないように

**anchor は答えが分かっているペア**です（**target 本人の録音 対 無関係な話者**）。

```bash
uv run python tools/blind_test.py prepare --a <系A> --b <系B> --out <dir> --seed <n> \
  --anchor-target t1.wav t2.wav t3.wav --anchor-foil f1.wav f2.wav f3.wav
```

| 設計 | 理由 |
|---|---|
| **正解は `anchors.json` にだけ置く** | **ページにも `key.json` にも出しません。** 正解が出たら catch trial の意味がありません（テストで固定） |
| 左右は clip ごとに振る | 常に A が正解だと並びを覚えられます |
| anchor も `audio/` / `paired/` に同じ命名で置く | **ページ側のコードは変更不要**です |
| `tally` は anchor を勝敗に入れない | `key.json` に無いので既に除かれます。**別に採点**して読み方の門にします |
| **引き分けは不正解** | target 本人 対 無関係な話者で引き分けなら、判別できていない印です |
| 未記入は不正解にしない | **未記入と間違いを混同しない**（正解率は回答分で出します） |
| 合格線は **75%** | これを下回ると `task_performed: false` |
| **anchor だけ両側を同じ sample rate へ落とす** | 素材が別コーパスから来ます（実測で波音リツ 44.1k / 棗 48k / 鬼灯 96k）。**片側だけ触ると帯域が「どちらが target か」の手がかり**になるので、両側を対称に落とします。**A / B の系ペアは揃えず例外のまま**（そちらは測定の契約） |

**動作確認（anchor をわざと全部外したシートを通した）:**

```text
  anchor（catch trial）: 正解 0 / 不正解 2 / 引き分け 0 / 未記入 0
  ** anchor を外しています。**本番の拮抗を「2 系が同一」と読まないこと**
     ―― 判別できていない可能性があります **
```

### 2a の事前登録（2026-09-16 決定。**回す前に書いた**）

#### 何を確かめるか

**低音 source をどれだけ移調すべきか。** いま男声には既定で **+12 半音**を渡していますが、
根拠は「+7〜+12」という範囲だけで**掃引していません**。台帳の実測 F0 から、
`natsume`（p50 **206 Hz**）→ リツ（p50 **360 Hz**）の理論値は **+9.7 半音**で、
**+12 は行き過ぎの可能性があります**。

#### 設定

| 項目 | 値 | 理由 |
|---|---|---|
| source | **`natsume`** の未使用曲から 8 clip | 低音（p50 206 Hz）。**日本語なので CER が読める** |
| 移調 | **+0 / +7 / +10 / +12** | 無移調 / 文書の下限 / **理論値（+9.7 の丸め）** / **現在の既定** |
| checkpoint | GAN `ckpt_015000` / 16 step / V3.1 | 採用中の系 |
| 再学習 | **なし** | `num_steps` を 16 に決めたのと同じ形 |

#### 上限は **transpose 0 で 1 度だけ作り、全 transpose で使い回します**

**理由:** CER の参照は **source の書き起こし**です。上限まで移調すると、「ボコーダー由来の
劣化」に**移調の影響が混ざり**、transpose どうしを比べられなくなります。

**注意（実装の発見）:** `svc_convert.py` は `--self-check` の上限にも**移調後の f0** を
渡しています（`mel_to_wav(vocoder, feats["mel"], logf0, ...)` の `logf0` が移調済み）。
つまり**何もしないと上限が transpose ごとに変わります**。`--ceiling-from` で
**transpose 0 の上限を固定**することで回避します。

#### 判定規則

| | 規則 |
|---|---|
| **主要な判定** | **話者類似度（target への回復率）が最大**。**移調はそのために入れた手**だから |
| **制約** | **CER の上限との差が、+0 の値から 5 点を超えて悪化しない** |
| **選び方** | 制約を満たすもののうち話者類似度が最大。同点なら **CER が小さいほう** |
| **記録するが判定に使わない** | 明るさ（centroid の上限比）、内容 cos。**細部比と同じ理由で、量は目的ではない** |
| **失敗の形** | どの移調でも制約を満たさなければ、**移調では解けない**ことになり、③b（特徴抽出前の pitch augmentation）へ移ります |

#### 予想（**後付けを防ぐために先に書く**）

**+10 前後が最良**と予想します。理論値が +9.7 で、**+12 は行き過ぎ**、**+0 は暗くなりすぎる**
（出力のスペクトル傾斜が入力 F0 に強く従うため）という既知の実測からです。

**外れたとき（+12 が最良だったとき）に分かること:** 話者類似度は**単純な F0 の一致では
決まっていない**ことになります。そのときは理論値を根拠にした推論をやめ、**掃引の値をそのまま
使います**。

#### 2a の結果（2026-09-16）: **+7 を採用。それまでの +12 は両方の軸で劣る**

**確認済み:** 一次データは `out/m5/sweep_tr{0,7,10,12}/` と `out/m5/sweep_metrics/`。
**上限は transpose 0 のものが全条件で bit 一致**しています（8 / 8 × 3 条件）。

| 移調 | **回復率** | CER 変換 | CER 上限 | **上限との差** | 制約 |
|---|---:|---:|---:|---:|:--:|
| +0 | 66.7% | 20.8% | 8.3% | +12.4 点 | OK |
| **+7（採用）** | **90.8%** | 20.8% | 8.3% | **+12.5 点** | **OK** |
| +10 | 88.4% | 21.4% | 8.3% | +13.1 点 | OK |
| **+12（それまでの推奨）** | 81.6% | **35.3%** | 8.3% | **+27.0 点** | **NG** |

**+12 は両方の軸で劣ります。** 話者類似度で **−9.2 点**、CER は制約（+0 の 12.4 点 + 5 点
= **17.4 点**）を大きく外れます。**事前登録した規則がそのまま +7 を選びました。**

#### 予想は外れました（記録する）

**「+10 前後が最良」と予想しましたが、+7 でした。** 理論値の F0 一致（`natsume` 206 Hz →
リツ 360 Hz で **+9.7 半音**）**より少ない移調のほうが良い**という結果です。

**事前登録に書いたとおりに読みます:** **話者類似度は単純な F0 の一致では決まっていません。**
理論値を根拠にした推論はやめ、**掃引の値をそのまま使います**。

#### 明るさとは順位が違います（記録のみ）

| 移調 | 変換 centroid | リツ本人（1160 Hz）との比 |
|---|---:|---:|
| +0 | 591 Hz | 0.51x |
| **+7（採用）** | 999 Hz | 0.86x |
| +10 | **1216 Hz** | **1.05x**（最も近い） |
| +12 | 1423 Hz | 1.23x |

**明るさが最も近いのは +10、話者類似度が最良なのは +7 で、一致しません。**
**判定軸を 1 つに決めて先に登録しておいたので、ここで迷わずに済みました。**
（明るさは「細部比と同じで量は目的ではない」として判定から外してあります。）

#### 日本語 test set が効いています

**8 / 8 clip が使用可能**でした（上限判別不能ゼロ、ASR 失敗ゼロ）。VocalSet では 26 中 18 しか
使えず、**日本語は 5〜6 本だけ**でした。

#### この測定の限界

- **n = 8、1 話者（`natsume`）、1 target（リツ）**です。**別の声では測り直すこと。**
- source は **既知話者・未知曲**です（`natsume` は base に入っています）。
- **+7 と +10 の差は 2.4 点**で、**n=8 では区別できない可能性があります**。
  **はっきり言えるのは +12 が劣ること**です。規則どおり最大の +7 を採りますが、
  **+7 と +10 のどちらかを強く主張はしません。**

### ④ M6 の前提が変わった（確認済み）

M6 の当初の組み立ては「non-causal teacher を causal student へ蒸留して実時間にする」でした。
**RTF の内訳を測って、この前提は半分だけ正しいと分かりました。**

| 量 | 何が効くか |
|---|---|
| **lookahead（遅延）** | **student の因果化が効きます。** 当初の組み立てどおり |
| **RTF（処理量）** | **ボコーダーが 93%。** acoustic を速くしてもほとんど動きません |

**したがって M6 の最初の作業は蒸留ではなく、ボコーダーの実行経路の測定です。** 現状は
NHVSing を **ONNX で CPU 実行**しています。GPU EP・chunk 分割・overlap を実測しないまま
student を作ると、**lookahead は縮んだが実時間では回らない**という結果になり得ます。

**`realtime_capable` を根拠にしないこと。** これは `rtf_total < 1` を見ているだけで、
chunk 境界も audio I/O も連続運転も見ていません。

## M0. データ確定

### 目的

学習・評価・配布のすべてが素材の権利と品質に依存します。ここを曖昧にしたまま先へ進むと、後段の成果物ごと使えなくなるため、最初に固定します。

### ゴール

次の 5 つが揃った状態を完了とします。

1. target singer と multi-singer corpus について、**学習可否・fine-tune 可否・重み配布可否・生成音声の利用条件**を規約 URL と取得日つきで記録した dataset ledger がある。
2. 全素材について clipping、伴奏漏れ、強い reverb、sample rate 誤りの検査を通し、除外したものは reject reason つきで残してある。
3. 音域（low/mid/high の滞在時間）と発声スタイル（chest / falsetto / breathy / 強声 / 弱声）の coverage を集計してある。
4. **base corpus が NHVSing にとって in-distribution かを判断してある。** 同梱ボコーダー NHVSing V3 は 本プロジェクトと同一の mel 仕様（44.1 kHz / hop 256 / 128-mel / 40–16000 Hz ln）で、特定の 10 コーパスで学習されています（[台帳](svc-dataset-ledger.md) 7 節）。そこに含まれない歌手の mel は vocoder にとって未知になり得ます。**ground-truth mel の再合成忠実度**を既知/未知のコーパスで比較して判断します。
5. train / validation / test を**曲単位・収録セッション単位**で分離した split list があり、seed が記録されている。未知 source singer の test set が別に用意されている。**性別で層化する**（実データで偏りを確認済み）。

### 成果物

dataset ledger（権利・lineage・checksum）、split list、reject list、coverage 集計。

### 進捗（2026-08-30）: 入手可能な素材について完了

**確認済み: 5 つのゴールすべてを実データで実行しました。** 詳細と数値は

| ゴール | 実施内容 |
|---|---|
| 1. dataset ledger | 既存 3 DB の権利条件を一次資料から記録。公開コーパス 14 件のライセンス調査。fork 元と同梱 NHVSing の学習データ。取得物の SHA-256。**素材の割り当てを確定** |
| 2. reject list | 5 コーパス全件に検査。理由つきで記録 |

| 4. NHVSing の in/out-of-distribution | **実測して判断済み**。ground-truth mel の再合成忠実度を 5 コーパス × 12 clip で比較し、**GTSinger にペナルティは見えない**（[台帳 7b 節](svc-dataset-ledger.md#7b-nhvsing-にとって-in-distribution-かの実測2026-08-30)） |

代表例: 歌手 ID の取り違えと曲名正規化の欠如による **leakage の実検出**、
split の性別偏り、帯域閾値 16 kHz が実歌唱に対して厳しすぎたこと（推奨を撤回）、

## M1. 特徴抽出前処理

### 目的

WAV から `svc_shard.npz` を作れないと SVC 学習を 1 度も回せません。ここが直列経路の最大のボトルネックでした。

同時に、この段階で決めた抽出条件は以降のすべての実験の比較基盤になります。後から変えると M2 以降の結果が全部無効になるため、再現性の記録をゴールに含めます。

### ゴール

**実装は TDD で行います**（[進行ルール](#9-進行ルール)）。以下の 1〜4 は、実装より先に書いて失敗させたテストで担保されている状態を指します。

1. `preprocess` 配下のコマンド 1 本で、WAV ディレクトリから `data/<db>/{metadata.json, svc_shard.npz}` が生成できる。
2. 生成した shard を `SVCFeatureDataset` が**例外なく**読める。`content` `f0_interp` `uv` `loudness` `mel` の `T` が完全一致している（loader は暗黙補正しないので、ここが通ることが整合性の証明になります）。
3. phrase 名が `{song}_{NNNN}` 形式である。`_song_of()` による曲単位 train/eval 分割が効かなくなるため、この命名を崩さない。
4. 同じ WAV・同じ設定で 2 回実行し、出力が **bit 一致**する。
5. manifest に次を記録している: content encoder の **model revision と層番号**、sample rate、hop、**SSL の stride と mel grid への補間方法**、正規化方法、**256 次元部分集合の index と生成 seed**、loudness の定義（窓幅・floor・正規化単位）、F0 extractor の version、入力 WAV の checksum。
6. 重いモデル（ContentVec / RMVPE）を落とさずに走る単体テストと、実モデルを使う統合テストが分かれている。前者が `test_*.py` の既定、後者は明示的に指定したときだけ動く。

### 決定（[content encoder の選定](svc-content-encoder.md)）

| 項目 | 決定 |
|---|---|
| content encoder | ContentVec（`lengyue233/content-vec-best`、MIT、768 次元、layer 12）を凍結して使う |
| 学習時の次元 | 768 から固定ランダムに選んだ **256 次元**（seed 0 を既定）。生の 768 は cache に、shard には 256 を書く |
| 補間 | SSL 50 Hz -> mel grid へ **left（直前保持・左寄せ繰り返し）**。先読み 0 ms、元の SSL ベクトルを保持 |
| F0 extractor | **RMVPE に固定** |
| loudness 特徴量 | **dataset 統計で正規化**（phrase 単位ではない） |
| 音声側の正規化 | RIFT-SVC に倣い **-18 LUFS** を検討。loudness 特徴量の正規化とは別レイヤ |

### 成果物

抽出コマンド、preprocessing manifest、target singer 1 人分の shard。

### 前提・依存

実行環境（Python 3.13 + CUDA 版 torch、`uv.lock`）と疎通確認は整備済みです。

**M0 との関係を分けます。** 抽出器の**実装とテストは M0 の完了を待たずに始められます**（テストは合成音声と小さな fixture で書けるため）。一方 M1 の**完了**（target singer 1 人分の実 shard）は M0 を要します。この分離により、権利確認と並行してコードを進められます。

### 抽出は 2 段に分ける

**決定:** 抽出器は次の 2 段構成にします。入口のコマンドは 1 本のままで、2 段目だけの再実行もできるようにします。

| 段 | 入力 -> 出力 | コスト | 内容 |
|---|---|---|---|
| 1. `extract` | WAV -> 生特徴 cache | 重い（GPU・モデル） | ContentVec 768 を 50 Hz のまま、RMVPE の F0、RMS、mel |
| 2. `build-shard` | cache -> `svc_shard.npz` | 軽い（CPU のみ） | mel grid への整列、dataset 統計での正規化、256 次元の切り出し |

**理由:** 下の 2 つの決定はどちらも「後で変えたくなる」種類のものです。2 段に分けておけば、**補間方法と 256 次元 seed の比較が 2 段目の再実行だけで済み、ContentVec と RMVPE を回し直さずに ablation できます。** vast.ai の課金に直接効きます。

shard に書くのは 256 次元です（768 ではありません）。loader に切り出しをさせると「暗黙に直さない」という契約の性質を崩すためです。

### 決定 1: 補間は left（直前保持）

**確認済み（実測）:** SSL は 16 kHz・stride 320 = 50 Hz、mel grid は 44,100/256 = 172.265625 Hz。比 3.4453125 は整数になりません。3 方式を同条件で測った結果:

| 方式 | left 基準の先読み | ブレンドされるフレーム |
|---|---:|---:|
| **left（直前保持）** | **0 ms** | **0%** |
| nearest | 20 ms | 0% |
| linear | 20 ms | 99.4% |

**決定:** **left** を採用します。理由は 3 つで、いずれも他方式より劣る点がありません。

1. **先読み 0 ms。** nearest と linear は 1 SSL フレーム（20 ms）先を読みます。[M6](#m6-streaming-student) は lookahead を削る作業なので、前処理の時点で無償の 20 ms を積むのは筋が悪く、しかも train と inference の因果性がずれます。
2. **元の SSL ベクトルをそのまま保持。** linear は 99.4% のフレームを混ぜます。ContentVec の表現空間が線形とは限らず、音素境界をまたぐ混合は実在しないベクトルを作ります。
3. **so-vits-svc の既定（`repeat_expand_2d` の `mode='left'`）と一致。** 最も広く使われている挙動です。

以前この文書では「推奨: まず linear」と書いていましたが、実測の結果 **left に訂正**しました。

### 決定 2: 256 次元は seed 0 を既定、M2 で seed 1 と比較

**決定:** 既定は seed 0。M2 の overfit で seed 1 との差を見ます。Interspeech 2025 の 2 つの部分集合は SSIM 0.813 / 0.822 と小さいながら差があったため、1 回だけ確かめます。2 段構成なので追加コストは 2 段目の再実行だけです。

**未実装だが選択肢として残す:** cache に 768 が残るので、ランダム部分集合ではなく PCA や学習可能な射影も後から試せます。

**注意:** SVC では online `pitch_aug` が使えません（`train.py` が SystemExit します）。augmentation を行うならこの段階、特徴量抽出の前に行います。RMVPE はマルチプロセスで動かさないこと。

### 進捗（2026-08-30）: 完了

**確認済み:** WAV ディレクトリから shard までコマンド 1 本で作れます。実装は
`preprocess/svc/{chunk,extract,encoders,shard,run}.py`、テストは `test_svc_preprocess.py`
（84 件。重いモデルを使わない）と `test_svc_preprocess_integration.py`（実 ContentVec / RMVPE、
既定 skip）です。

## M2. 実音声 smoke

### 目的

完了レベル 2（合成テンソル）と 3（実データ）の間を埋めます。**この段階の成功は音質も一般化も意味しません。** loader → condition → flow → vocoder の実配線が、実際の音で最後まで通ることだけを確認する工程です。

### ゴール

1. 1〜数 phrase を train set とし、loss が十分低下するまで overfit できる。
2. checkpoint から mel を生成し、NHVSing で WAV にできる。**完了レベル 3 の到達判定はこの WAV の存在**とします。
3. 出力 WAV を聴き、F0 の追従、無声区間の位置、長さが入力と整合している。
4. 同じ入力・seed・checkpoint で再実行し、結果が再現する。
5. 学習時と推論時で特徴量の正規化が同一であることを検証してある。

### 成果物

overfit run の log、生成 WAV、再現性の確認記録。

### 進捗（2026-08-30）: 完了

**確認済み:** vast.ai の RTX A4000 インスタンス（$0.098/hr、約 27 分、実費 約 $0.04）で
波音リツ 2 phrase（各 3 秒）を 3,000 step overfit し、WAV を生成しました。
検証は [`tools/m2_verify.py`](../tools/m2_verify.py)、報告は `m2_report.json` です。

| ゴール | 結果 |
|---|---|
| 1. overfit できる | flow 0.00710 → 0.00235（最小 0.00115、**3.0 倍**）、recon 0.03573 → 0.01889（最小 0.00193） |
| 2. **WAV を生成できる** | **`m2_pred.wav` 3.00 秒 / 44.1 kHz / peak 0.950。完了レベル 3 の到達判定を満たす** |
| 3. F0・無声・長さの整合 | 長さ 132,096 = 516 × 256 で一致。**F0 相関 0.9991・中央値 0.012 半音・p90 0.075 半音**、V/UV 一致率 0.988 |
| 4. 再現性 | 決定的モードで **bit 一致**（max diff 0.0） |
| 5. 学習と推論で正規化が同一 | `features_to_item()` が manifest の統計と部分集合を当て、**shard の値と 1 bit も違わない**ことをテストで固定 |

**切り分け:** ground-truth mel を NHVSing に直接通した WAV も出しました。GT 側の F0 相関 0.9990 /
中央値 0.012 半音に対し、予測側は 0.9991 / 0.012 半音で**ほぼ同等**です。したがって
**この phrase では音響モデルが vocoder の性能を損なっていません**。

#### この過程で見つかった欠陥 2 件

**1. 無声だけの phrase が学習に入っていた（M1 の欠陥）。** 最初の overfit で生成された WAV が
無音になりました。追うと入力の `uv` が全フレーム 0 で、曲の先頭 27 秒がイントロの無音だったためです。
固定長で先頭から切ると、**89 chunk 中 35 件（39%）が完全に無声**になっていました
（しきい値 0.5 で最終的に除外されたのは 39 件、採用は 50 phrase）。
`chunk.py` に `voiced_ratio()` を足し、抽出時に `--min-voiced`（既定 0.3）未満を捨てるようにしました。
除外後は有声率が最小 0.516 / 平均 0.857 になりました。**合成データでは出ない欠陥です。**

**2. CUDA 推論が bit 再現しない。** 切り分けたところ RNG ではなく CUDA の conv/matmul の
非決定性でした（CPU は bit 一致、CUDA は max 7.95e-02 / mean 4.33e-04 の差）。
`torch.use_deterministic_algorithms(True)` と `CUBLAS_WORKSPACE_CONFIG` を有効にすると
**CUDA でも bit 一致**します。検証スクリプトでは既定で有効にしました。

### 前提・依存

M1 完了。

### 打ち切り・巻き戻し条件

WAV が出ない、または明らかに入力と対応しない場合、原因が前処理（M1）にあるか配線にあるかを切り分けるまで M3 へ進みません。ground-truth mel を NHVSing に直接通した音と比較すれば、音響モデルの誤差と vocoder の誤差を分離できます。

## M3. multi-singer base pretraining

### 目的

target singer 単独で学習すると、SSL content に残った話者性を利用する近道を学んでしまい、**未知の source singer を入れたときに崩れます**。それを避けるため、複数歌手の自己再構成を speaker 条件つきで学習し、content / pitch / loudness と話者性が分離した土台を作ります。

### ゴール

1. 複数歌手の shard で `model.n_speakers` / `data.spk_map` / `train.balance_speakers` を設定し、speaker-balanced sampling で学習が完走する。
2. base checkpoint を **immutable な入力として保存**してある（M4 以降が上書きしない別ディレクトリ）。
3. 学習済みでない source singer を入れたとき、歌詞内容が崩壊しない。
4. 最初の 100 / 1,000 update で examples/sec、frames/sec、peak VRAM、checkpoint size、validation time を実測し、[データセットと計算資源](svc-data-compute.md) の見積もりを実測値へ更新してある。

### 成果物

base checkpoint、学習曲線、実測したスループットと VRAM、更新済みの見積もり表。

### 前提・依存

M2 完了、および M0 で multi-singer corpus の権利が確定していること。両方とも満たしています。

### 開始時にやること（base 学習の前に）

**決定:** M1 決定 2 の **seed 0 / seed 1 比較**をここで片づけます。インスタンスを立てた直後、
base 学習を始める前に、同じ split・同じ seed・同じ更新 budget で 2 本の overfit を回して
比較します。専用インスタンスを立てずに済み、追加は数分です。

```bash
# 2 段目だけを 2 通り回す（ContentVec / RMVPE の再実行は不要）
uv run python -m preprocess.svc.run --from-cache data/ritsu/_cache --out data/seed0 --subset-seed 0
uv run python -m preprocess.svc.run --from-cache data/ritsu/_cache --out data/seed1 --subset-seed 1
# run 名を分けて 2 本。base checkpoint は別 run_name（上書きしない）
uv run python -m train --config configs/svc_base.yaml --data_dirs data/seed0 \
  --run_name svc_seed0 --out_root log --device cuda --max_updates 3000
uv run python -m train --config configs/svc_base.yaml --data_dirs data/seed1 \
  --run_name svc_seed1 --out_root log --device cuda --max_updates 3000
uv run python tools/m2_verify.py --ckpt log/svc_seed0/ckpt_003000.pt --data data/seed0 --out out/seed0
uv run python tools/m2_verify.py --ckpt log/svc_seed1/ckpt_003000.pt --data data/seed1 --out out/seed1
```

差が無ければ seed 0 で確定し、以後の全実験の基盤にします。差が出たら、その差を
[content encoder の選定](svc-content-encoder.md) へ記録してから base 学習へ進みます。

### 素材の構成

**決定:** [台帳](svc-dataset-ledger.md) 6 節の割り当てに従い、**GTSinger 全 9 言語 20 歌手 +
日本語 3 DB** を使います。用意は [`tools/m3_corpus.py`](../tools/m3_corpus.py) が行います。

| 決定 | 内容 |
|---|---|
| 話者ごとに 1 shard ディレクトリ | `svc_dataset.py` は speaker id を**ディレクトリ名**から引く（`spk_map`）。話者を分けるにはディレクトリを分けるしかない |
| 波音リツ 3 音源は同じ speaker id | 同じ歌手の別の声質。SVS 側の config と同じ扱い |
| **歌手ごとに分量を揃える**（`--max-hours`） | base 事前学習で効くのは総時間より**話者の多様性**。GTSinger 80.59 h を全部抽出すると 12 時間以上かかる |
| GTSinger は使う wav だけ落とす | リポジトリは 149,037 ファイルあり、丸ごと落とすと HTTP 429 で律速されて 3 時間半かかる（実測） |
| 曲名は `--song-parts` で指定 | `<言語>/<歌手>/<技法>/<曲>/<Group>/NNNN.wav` の `<曲>`。技法や Group をまたいで同じ曲を同じ song 名にしないと leakage する |

`--write-config` が**実際に作った shard から**埋めた config を run ディレクトリへ書き出します。

#### 試聴で見つかった欠陥 2 件（2026-08-30、M3 完了の宣言後）

**確認済み:** 利用者が出力を聴いて「音がこもっている」と報告したことから、次の 2 件が出ました。
**どちらも M3 の検証一式（content cos / F0 相関 / V/UV）を素通りしていました。**

**1. 推論ツールが入力を peak 正規化していた（学習と条件が違う）。** `preprocess.svc.run` は
生の音量のまま特徴を取りますが、`tools/m3_verify.py` と `tools/svc_convert.py` は
peak 0.95 へ揃えてから抽出していました。波音リツの DB は peak 0.107 と小さく、**実質 19 dB の
増幅**になります。loudness 条件が学習分布（mean −4.63 / std 1.69）の **1.2σ 外**へ出て、
モデルが低域を持ち上げ高域を削っていました。

| リツ自己再構成（8 秒） | mel L1 | 低域 bin 差 | 高域 bin 差 | centroid |
|---|---:|---:|---:|---:|
| 修正前（peak 正規化） | 0.727 | +0.439 | −0.636 | 368 Hz |
| **修正後（生の音量）** | **0.558** | +0.101 | −0.236 | **620 Hz** |

M2 ゴール 5「学習時と推論時で正規化が同一」は `features_to_item()` で保証していましたが、
**その手前で波形を加工していた**ので、保証の境界の外側で破れていました。両ツールを直し、
peak 正規化は `--peak-normalize` の明示指定でしか起きないようにしています。

**2. 検証指標が高域の欠落を検知しない。** この不具合で spectral centroid が 620 → 368 Hz へ
落ちても、**content cos は 0.8217 → 0.8096 としか動きませんでした**。F0 相関も V/UV も同様です。
内容・音高・有声区間だけを見ていると、音の明るさの劣化は素通りします。
[`tools/audio_metrics.py`](../tools/audio_metrics.py) に帯域エネルギー比と centroid を切り出し、
`m3_verify` の報告へ載せました（契約テスト 6 件）。

**M3 ゴール 3 の結論は変わりません。** 修正後に測り直しても content cos 0.799〜0.810 /
回復率 84% 前後で、バグの有無にほぼ依存しませんでした（指標が鈍感だったため）。

**残る鈍さは「モデルの限界」ではなく「1 step 写像の未収束」でした（2026-08-30 追測）。**

利用者の再度の指摘（「まだこもっている／つぶれている」）を受けて flow の step 数を振ったところ、
**step を増やすと明るさが戻ります**。上限（GT mel をボコーダーに通した再合成）との差は次のとおり。

| 区間 | 上限 | **1 step** | **16 step** |
|---|---:|---:|---:|
| 波音リツ 1st_color | 875 Hz | 651（−26%） | 711（−19%） |
| 波音リツ anywhere | 1282 Hz | 1021（−20%） | 1197（**−7%**） |
| 波音リツ ARROW | 775 Hz | 745（−4%） | 856（**+10%**。行き過ぎ） |
| 持ち込み音源（音量合わせ後） | 1499 Hz | 1186（−24%） | 1357（**−9%**） |
| **平均** | — | **約 −17%** | **約 −5%** |

**これは診断として重要です。** よく学習された rectified flow なら 1 step と多 step の結果は
ほぼ一致するはず（それが rectification の目的）で、**差が出ること自体が 1 step 写像が
まだ真っ直ぐになっていない証拠**です。学習継続（「M3 の後の分岐」の①）の根拠が強まりました。

**注意:** 16 step は flow の評価回数が 16 倍で、このリポジトリの売りである 1-step とは別の設定です。
**ここで測った「モデルの高域不足」は推論設定に依存します。** 以前この節に書いていた
−4〜−26% は 1 step 時の値でした。比較するときは step 数を必ず併記してください。
また ARROW の +10% のように**行き過ぎる**こともあり、多 step が常に良いわけではありません。

**8–16 kHz だけは推論設定で戻りません**（持ち込み音源で 0.9% 対 上限 2.9%）。最高域の再現は
学習か GAN の領域です。

**つぶれ（変化量の減少）は軽度でした。** GT 比で時間方向 std 0.92〜0.96、周波数方向 0.91〜0.94。
聴感の「つぶれ」の主因は変化量ではなく**帯域の偏り**（低域に山が寄り、1–2 kHz が上限の半分以下）です。

**話者条件は強く効いています。** `spk_id` を変えると mel が 0.82〜1.20 ln-mel 動きます。
配線や条件付けの問題ではありません。

**ボコーダーは無罪です**（入力の 2–4 kHz を 4.1% → 3.9% とほぼ保つ）。mel を直接見ると、
**bin 80 以上（約 3 kHz 超）が −0.15〜−0.19 ln-mel 不足**し、2–3 kHz が +0.16 過剰でした。
全体の音量は合っています（mean 差 0.04）。`laplacian_var_ratio` は 0.869 で、
**1.0 を下回る＝やや潰れている**方向です。原因は学習不足（eval loss は 30,000 step でも
下降中）と mel の過平滑で、後者には GAN（[条件付きトラック C](#c-gan-の導入)）が設計上の対処です。

> **この段落の原因診断は 2026-08-31 に否定されました。** 学習不足でも過平滑でもなく、
> **出力のスペクトル傾斜が入力 F0 に強く従う**ことが原因です（下の
> 「[測り直した結果（2026-08-31）: 原因は学習不足ではなく入力の F0 だった](#測り直した結果2026-08-31-原因は学習不足ではなく入力の-f0-だった)」）。
> 60,000 step まで延ばしても、M4 の fine-tune を経ても解消しません。**以降の記述は当時の
> 記録として残しています。**

#### この過程で見つかった欠陥・修正 4 件

1. **phrase 名が衝突して cache を黙って上書きしていた。** GTSinger の深い構造で
   `song_name()` が親ディレクトリ（`Control_Group`）を返し、連番がファイルごとに 0 へ戻るため、
   1 歌手 1,922 ファイルが **3 つの名前に潰れて**いました。例外にもなりません。
2. **日本語の曲名がすべて消えていた。** 名前を ASCII に削っていたため、日本語題の曲が
   1,922 中 1,723 件で同じ名前になり、曲単位 split が効きませんでした。
3. **`eval_items` は話者ごとの本数。** 3 話者なら 9 サンプルですが 23 話者では 69 になり、
   1 回の eval が mel 図と音声を 138 本書き出して **10 分以上**（単一コア 100%）かかりました。
   多話者では `eval_items: 1` にします。
4. **GTSinger を丸ごと落とすと HTTP 429 で 3 時間半。** 使う wav だけ選んで 9 分にしました。

### 規模の目安

**見積もり:** 20〜50 人 / 合計 100〜300 時間が現実的な最初の本学習案です。ただしこれは実測前の計画値であり、より小さい corpus で先に recipe を確定させます。

**確認済み（実測後の補正）:** 今回は **23 話者 / 約 18 時間**（1 歌手あたり 0.75 時間）で
recipe が成立しました。**eval loss は 30,000 step でもまだ下がり続けており、
更新回数にも素材量にも伸びしろがあります。** 総時間より話者数を優先する構成は機能しています。

### 注意

**確認済み:** `train.py` は gradient accumulation を実装していません。config に `accum_steps` があっても無視されます。実効 batch を増やす計画を立てる場合、accumulation の実装とテストが先に必要です。

**決定:** この段階では GAN を無効のままにします（`gan.enabled: false`）。flow + 再構成が成立し、artifact を分類できる状態になってから、別 run で GAN を導入します（条件付きトラック C）。

### M3 の後の分岐（要ユーザー判断）

**確認済み:** M3 の base には**高域不足**が残っています（進捗節）。M4 へそのまま進むか、
先に base を改善するかは**素材でも設計でもなく、どこに時間と費用をかけるかの判断**なので、
利用者が決めます。3 択とその根拠を並べます。

| 選択 | 根拠 | 見積もり |
|---|---|---|
| **① 学習を続ける**（実施済み） | eval loss が 30,000 step でも**単調減少中**。さらに **flow の step 数を増やすと明るさが戻る**（平均 −17% → −5%）＝**1 step 写像が未収束**という直接の証拠がある | **実費 $2.148 / 約 2 時間 50 分**（下の実施結果）。当初「約 1 時間・$0.3」と見積もったが、**素材の再生成 69 分と通信課金 $0.87 を数えていなかった** |
| **② GAN を別 run で入れる**（トラック C） | `laplacian_var_ratio` 0.869（1.0 未満＝潰れ気味）。過平滑への**設計上の対処**で、起動条件は満たした | base と同じ budget の A/B が要る。①より高く、不安定化の risk もある |
| **③ M4 へ進む** | 本来の次工程。target 固有の細部が乗るので**高域不足も一緒に軽くなり得る** | M4 の見積もりどおり。base の欠点を持ち越す risk はある |

**①は実施済みです（下の結果）。** 仮説どおり 1 step 写像は真っ直ぐになりましたが、
**clip ごとのばらつきが大きく、3 本中 1 本は悪化しました**。

**次にやるべきは②③のどちらでもなく、測り直しです。** n=3 では「さらに継続すべきか」を
判断できません。**clip 数を増やした再測定は手元の CPU でできます**（インスタンス不要・費用ゼロ）。
[`tools/m3_verify.py`](../tools/m3_verify.py) と
[`tools/audio_metrics.py`](../tools/audio_metrics.py) がそのための道具です。

- 30,000 step 版と 60,000 step 版の checkpoint は**両方とも手元にあります**（`.m0data/m3c/`、
  `.m0data/m3/`）。同じ clip 集合で 1 step と 16 step を測れば、追加の課金なしで比較できます。
- **10〜20 clip まで増やす**と、BC+-6 のような悪化が外れ値なのか傾向なのかが分かります。
- その結果を見てから「さらに継続」「②GAN」「③M4 へ進む」を判断します。**①②③のどれを選んでも、進む前に
[`tools/m3_verify.py`](../tools/m3_verify.py) の spectral centroid を base と比較すること**
（内容指標は高域の欠落を検知しません）。

**やってはいけないこと:** 高域不足を「そういうもの」として素通りし、M5 の品質比較まで持ち越す。
比較の時点で原因の切り分けができなくなります。

### ①を実施した結果（2026-08-31）: 仮説は確認された

**確認済み:** 30,000 → **60,000 step** まで継続しました（RTX 4090、**11.74 step/s**）。
成果物は `.m0data/m3c/`（`ckpt_060000.pt` と実験記録）です。

| 成功条件 | 結果 |
|---|---|
| ① 60,000 step 完走 | **達成**。`[resume] ckpt_030000.pt -> step 30000` から継続 |
| ② eval/loss が 0.02311 より下がる | **達成**。**0.01459（−37%）**。40k 0.01637 → 50k 0.01507 → 60k 0.01459 と**まだ下降中** |
| ③ 1 step と 16 step の差が縮む | **達成**。**10.8 → 6.0 点** |

同一クリップで測り直した比較（3 本）:

| | 1 step | 16 step | 乖離 |
|---|---:|---:|---:|
| 30,000 step | −18.1% | −7.3% | **10.8 点** |
| **60,000 step** | **−13.7%** | −7.7% | **6.0 点** |

**1 step が多 step へ寄った**（−18.1% → −13.7%）一方で 16 step はほぼ動いていません。これは
**1 step 写像が真っ直ぐになった**という仮説どおりの動き方です。eval/flow も 0.00620 → 0.00413、
eval/recon は 0.03383 → 0.02093 に改善しました。

**ただし clip ごとにばらつきます（n=3）。**

| clip | 1 step 30k → 60k | 16 step 30k → 60k |
|---|---|---|
| 1st_color | −25.5% → **−9.0%** | −17.0% → **−2.1%** |
| ARROW | −4.4% → −6.0% | +6.3% → **+0.4%** |
| BC+-6 | −24.2% → −26.2% | −11.1% → **−21.6%** |

1st_color は大きく改善、ARROW は行き過ぎが減り、**BC+-6 は悪化**しました。
平均は改善していますが、**一律に良くなったわけではありません**。

**次の判断:** eval loss はまだ下降中なので、さらに継続する余地があります。ただし
**BC+-6 のような悪化例があるため、step 数を増やせば単調に良くなるとは言えません**。
**次の課金の前に、手元の CPU で clip 数を増やして測り直します**（上の「次にやるべきは
測り直しです」）。checkpoint は 30,000 / 60,000 の両方が手元にあります。

**→ 測り直しました。下の節で、この判断も「高域不足＝学習不足」という見立ても差し替わります。**

### 測り直した結果（2026-08-31）: 原因は学習不足ではなく入力の F0 だった

**確認済み:** n=3 を **40 clip（VocalSet 20 歌手）** へ広げ、30,000 / 60,000 step ×
1 / 16 step の 4 通りを手元の CPU で測り直しました（**38 分・費用ゼロ**）。成果物は
`.m0data/m3re/` の `m3_report.json` です。

**まず測り方に誤りがありました。** centroid 上限比の**符号つき平均**を見ていましたが、
clip の半分は上限より明るく（最大 +33%）半分は暗い（最大 −70%）ので打ち消し合います。
**ceiling からの距離（絶対値）**で測り直すと像が変わります。

| 上限比の絶対値の平均 | 1 step | 16 step | 乖離 |
|---|---:|---:|---:|
| 30,000 step | 37.7 | 41.1 | 3.4 点 |
| **60,000 step** | **34.3** | **34.0** | **0.2 点** |

**①の根拠は消えました。** ①を選んだ理由は「多 step にすると明るさが戻る＝1 step 写像が
未収束」でした。60,000 step では 1 step と 16 step が実質同等（**0.2 点差**）で、
**これ以上 step を回しても 1 step 品質は改善しません**。なお 30,000 step 時点の
「多 step で明るさが戻る」という観察自体も符号つき平均による見かけで、絶対値では
16 step のほうが悪い（明るい clip で行き過ぎる）ものでした。

**偏差には構造がありました**（60,000 step / 1 step / target = 波音リツ）。

| 群 | n | 上限比 |
|---|---:|---:|
| 歌唱・女性 | 9 | **+16.1%** |
| 歌唱・男性 | 11 | **−38.1%** |
| 話し声・女性 | 9 | −29.9% |
| 話し声・男性 | 11 | −46.1% |

男女の歌唱は **source の明るさが同じ**（884 Hz 対 889 Hz、上限も 895 対 922）なのに、
**同じ target** へ変換すると 540 Hz 対 1067 Hz になります。target を男性
（JA_Tenor_1）へ替えても男性 source は 535 Hz で動きません。**target 側の問題ではありません。**

**確認済み: 原因は条件として与える F0 です。** `transpose_f0` で content と loudness を
固定したまま F0 だけを動かすクロスオーバーを行いました（同じ 40 clip、target = 波音リツ）。
**上限（GT mel の再合成）にも同じ移調 F0 を渡す**ので、音高が下がれば centroid も下がる
という当たり前の効果は比から落ちます。

| 群 | −12 半音 | 0 | +12 半音 |
|---|---:|---:|---:|
| 歌唱・男性（変換後の絶対値） | 250 Hz | 540 Hz | **1196 Hz** |
| 歌唱・女性（変換後の絶対値） | 378 Hz | 1067 Hz | 1140 Hz |

**男性 source を 1 オクターブ上げるだけで、女性 source をそのまま変換した明るさを超えます。**
逆に女性を 1 オクターブ下げると 378 Hz まで落ちます。出力のスペクトル傾斜は source の
性別でも target でもなく、**条件の F0 に従います**。

**仮説（未検証）:** rectified flow の出発点 `x0` は F0 から作る擬似 mel です。F0 が低いと
倍音が密になり傾きが変わるため、モデルが励起の傾きを出力へ写している可能性があります。
学習データ側の自然な相関（高い音ほど明るい）も効いているはずです。いずれにせよ結合が
強すぎて、**男性の音高を女性 target の音色で鳴らせていません**（波音リツは C4–C5 中心で、
130 Hz を歌った素材が存在しません）。

**話し声には別の要因が残ります。** +12 にしても女性の話し声は −28.2%（0 のとき −29.9%）と
ほとんど動きません。学習素材が歌唱のみなので分布外であり、移調では直りません。

**分岐の結論:**

| | 判定 |
|---|---|
| ① 継続学習 | **不採用。** 根拠（1 step 未収束）が消えた |
| ② GAN | **不採用（今は）。** 過平滑への対処であって、F0 依存の傾斜は直さない |
| **③ M4 へ進む** | **採用。** ただし下の 2 条件を付ける |

1. **変換時の移調を運用規則にする。** male source → female target は **+7〜+12 半音**。
   `tools/svc_convert.py` と `tools/m3_verify.py` の `--transpose` です。
2. **base の pitch augmentation を検討対象として残す。** 話者ごとの音域を広げれば結合が
   緩みますが、SVC では**特徴抽出の前**に行う必要があります（online は `train.py` が拒否）。

## M4. target fine-tune（offline teacher）

### 目的

base の汎化を保ったまま、target singer の音色を再現します。この成果物が、以降のすべての比較と蒸留の基準（teacher）になります。

### ゴール

1. base checkpoint から target 専用の run directory で fine-tune し、base を上書きしていない。
2. **target similarity と、未知 source の明瞭度の両方**を記録してある。train 再構成だけが改善して未知 source が悪化する場合は早期停止する。
3. held-out song で変換した出力がある。
4. best checkpoint を train loss だけで選んでいない。選択規則が記録されている。
5. 各 run について実験記録が揃っている: Git commit と dirty diff、config の完全コピー、dataset manifest と split、依存 lock と CUDA / driver / GPU、seed、init checkpoint、failure list。

### 成果物

offline teacher checkpoint、指標一式、failure list、実験記録。

### 前提・依存

M3 完了。**base の状態を引き継ぐ点に注意します。**

- 入力は **`ckpt_060000.pt`**（23 話者 / 60,000 step / 141 MB、手元は `.m0data/m3c/`）。
  **別の `run_name` で fine-tune し、base を上書きしないこと**（M3 ゴール 2）。target は
  **spk_id 22**（波音リツ）。構造を変えないので `--init_from ... --finetune` が使えます。
- **base は「暗い」のではなく、出力の傾斜が入力の F0 に強く従います**（M3 測り直し節）。
  fine-tune 前後で [`tools/m3_verify.py`](../tools/m3_verify.py) の spectral centroid を
  **移調あり・なしの両方**で比較し、改善したのか持ち越したのかを必ず記録します。M4 の
  similarity 指標だけを見ていると、この軸は素通りします。
- **male source → female target の変換には `--transpose` を使うこと**（+7〜+12 半音）。
  移調なしの数値だけで M4 の成否を判定しないこと。
- **推論時に入力の音量を触らないこと。** 学習は生の音量で特徴を取ります。ここを揃えないと
  loudness 条件が学習分布からずれ、出力の高域が落ちます（M3 で実測。実質 19 dB の増幅になっていた）。

### 進捗（2026-08-31）: 実施済み。**target は良くなり、未知 source は悪くなった**

**確認済み:** RTX 3090 で 20,000 step の fine-tune を実施しました。成果物は `.m0data/m4/`

**target hold-out（ritsu 6 曲の自己再構成、1 step）:**

|---|---:|---:|---:|

**両者は単調に逆向きです。** step を進めるほど target は上限へ近づき（94.8% → 98.1%）、

選ばない）が 15,000 step で発動しました。

**選択した checkpoint: `ckpt_010000`。** 規則を通った 5,000 / 10,000 のうち eval/loss が
小さいほう（0.01157 対 0.01185）です。**train loss だけでは 20,000 を選んでいました。**

**確認済み: fine-tune では F0 依存の傾斜は直りませんでした。** 未知 source の明るさの偏差は
33.7 → 37.5 と悪化し、+12 半音でも base 30.0 対 ft 30.8 で変わりません。M3 の測り直しで
立てた見立て（「③M4 へ進んでも男性 source の暗さは直らない」）どおりです。

#### ゴール 2 の残り半分（2026-09-01 に測定）: **話者類似度も fine-tune で上がっていた**

**確認済み:** 話者照合 encoder を ECAPA-TDNN に替え、**12 秒以上**のクリップで較正を通した
（[評価計画](svc-evaluation.md) 4 節）ので、M4 ゴール 2 の未測定分を測りました。

未知 source（VocalSet 6 名 / 各 20 秒 / 男性は +12 半音）を波音リツへ変換し、
**上限**（リツの別クリップどうし 0.7202）と**下限**（同系統の UTAU DB = 鬼灯・棗 0.2862）に
挟んで読みます。

| checkpoint | 変換 対 target | **回復率** | female source（同性） | male source（異性） |
|---|---:|---:|---:|---:|
| base（60,000） | 0.4819 | **45.1%** | 46.2% | 44.0% |
| **ft 10,000（採用）** | 0.5244 | **54.9%** | 60.0% | 49.8% |
| ft 20,000 | 0.5380 | **58.0%** | 63.6% | 52.4% |

**fine-tune は target らしさを確かに上げています。** 内容保持が単調に落ちるのと**逆向きに、
話者類似度は単調に上がります**。M4 の trade-off は、これで両軸とも数字が付きました。

**異性間のほうが伸びません**（+8.4 点 対 同性 +17.4 点）。男性 source を女性 target へ寄せる
のは、移調しても依然として難しいということです。

**この測定の限界:**

- **1 群 3 clip、checkpoint あたり 6 clip**です。順序は明瞭ですが、幅は狭く見ないこと。
- **選択規則より後に測りました。** 規則（未知 source の内容保持）は事前登録どおり
  `ckpt_010000` を選んでおり、**この数字で選び直してはいません**。ft20000 は類似度で
  +3.1 点を買う代わりに内容保持を規則の外まで落とします。
- 上限に使ったリツのクリップは学習曲を含みます。上限はモデルを通さない量なので影響しませんが、
  **変換側は未知 source のみ**である点が重要です。
- **今後の選択規則には話者類似度も入れられます**（測れるようになったため）。M5 以降の
  fine-tune では、内容保持の下限と類似度の下限を**両方**事前登録するのが妥当です。

**費用:** 実費およそ **$0.75**（4.4 時間 × $0.16）。見積もり $0.35 の 2.1 倍でした。差は
GPU ではなく段取りです（鍵未登録で 15 分、スクリプトの不具合で 7 分、checkpoint の
回収が遅く約 40 分インスタンスを空回しさせた）。**次回は回収を先に細く始めるか、
checkpoint を選んでから落とすこと。**

### 規模の目安

**見積もり:** target singer 5〜10 時間が実用品質を狙う最初の推奨範囲です。ただし時間より coverage が重要で、5 時間あっても中音域の同じ歌い方だけなら高音裏声や強い子音で崩れます。

### 未決

**要ユーザー判断:** speaker embedding を残して target ID を固定するか、embedding を焼き込んで speaker 入力のないモデルにするか。**推奨:** base 学習中は話者条件を残し、固定化は fine-tune と配布の段階で判断します。

**決着（2026-09-01）: ゴール 2 の target similarity を測れるようになりました。**
枠組みは [`tools/speaker_similarity.py`](../tools/speaker_similarity.py)、較正は
[`tools/speaker_calibrate.py`](../tools/speaker_calibrate.py) で**再実行できます**
（VocalSet 20 歌手・excerpts/straight・各 3 本）。**合格条件は走らせる前に決めました**:
重なり（同一話者ペアの下位 5% を超える別話者・同性ペアの割合）が **20% 以下**。

| encoder | クリップ長 | 同一話者 | 別話者・同性 | 別話者・異性 | 重なり | 判定 |
|---|---:|---|---|---|---:|:--:|
| wavlm-base-plus-sv | 6 s | 0.8307 ± 0.0832 | 0.7713 ± 0.1104 | 0.5199 ± 0.1296 | 83.3% | 不合格 |
| wavlm-base-plus-sv | 12 s | 0.8856 ± 0.0670 | 0.8196 ± 0.0943 | 0.5314 ± 0.1323 | 77.0% | 不合格 |
| ECAPA-TDNN | 6 s | 0.5415 ± 0.1331 | 0.3452 ± 0.1325 | 0.1816 ± 0.0976 | 56.9% | 不合格 |
| **ECAPA-TDNN** | **12 s** | 0.6632 ± 0.0995 | 0.3891 ± 0.1369 | 0.1966 ± 0.1013 | **19.8%** | **合格** |
| **ECAPA-TDNN** | **20 s** | 0.7096 ± 0.1037 | 0.4040 ± 0.1386 | 0.2109 ± 0.1096 | **17.3%** | **合格** |

**encoder と長さの両方が要りました。** x-vector は 12 秒にしても 77.0% で不合格、ECAPA も
6 秒では 56.9% で不合格です。**2026-08-31 に「測れない」と結論したのは、6 秒に切って
測っていたことが原因の半分でした**（encoder だけを疑い、素材の条件を疑わなかった）。

そのため `similarity_report` は **12 秒未満のクリップを拒否**します。較正の外で数値を出さない
ための契約です。依存は `speechbrain`（`eval` extra）。**重みのライセンスは未確認**なので
内部指標としてのみ使います。

## 条件付きトラック (C') GAN fine-tune（2026-09-01 起動）

### なぜ起動するか

**確認済み:** M5 の調査で、話者性が弱い原因は**過平滑**だと特定しました（予測 mel の細部が
25% 欠ける。[M5 の調査節](#話者性が弱い原因の調査2026-09-01-過平滑step-を増やすと戻る)）。
**base も fine-tune も `gan.enabled: false`** で、flow 損失 + 再構成損失のみでした。

`num_steps` を 16 にして未知 source の回復率は 60.7% → 69.4% まで来ましたが、**Seed-VC
（0.5912）にはまだ届きません**（0.4910）。**残りは過平滑そのものへの対処が要ります。**

**傍証:** 同じ手元で動かしている [Beatrice](https://prj-beatrice.com)（別アーキテクチャ・
別 target・**GAN あり**）は、話者類似度の到達率 93.8% に達しています。**アーキテクチャも
データも違うので根拠としては弱い**ですが、GAN 付きの SVC が高い話者類似度に届くことの
実例ではあります。

### 案 A から始める（決定）

| 案 | 内容 | 費用 |
|---|---|---|
| **A（採用）** | 既存 base（60,000 step）から **GAN 有効で fine-tune** | 1〜2 時間 |
| B | base から GAN 付きで学習し直す | 8〜12 時間 |

**A を先に試します。** 安く、かつ「GAN で細部が戻るか」に答えられます。**base 自体が過平滑
なので効果が限定的な可能性はあります**が、戻らなければ B に進んでも同じでしょう。

**既存の `ckpt_010000`（M4 で選択）は上書きしません。** 比較対象として必要です。

### GAN 版で M5 を測り直した結果（2026-09-02）: **差は大きく縮んだが、まだ届かない**

**確認済み:** `ckpt_015000` で test set 26 clip を変換し直し、同じ指標で測りました。
一次データは `out/m5/metrics_gan/`、判定は `out/m5/guard_rail_gan.json`。

| 指標 | GAN 無し（16 step） | **GAN 有り** | Seed-VC | guard rail |
|---|---:|---:|---:|:--:|
| 話者類似度 | 0.4910 | **0.4981** | 0.5912 | **NG のまま**（**測定誤り。訂正後 0.5673 → 0.5886 対 0.5912**） |
| timing 対応率 | 71.9% | **73.7%** | 70.8% | ok（**Seed-VC を上回る**） |
| F0 相関 | 0.9995 | 0.9994 | 0.9978 | — |
| V/UV 一致 | 99.1% | 99.0% | 98.7% | — |
| SQUIM stoi（上限との差） | −0.019 | **−0.008** | 測れない | — |

**判定: 「Seed-VC より良い」は依然として書けません。** 差は −0.100 から −0.093 へ縮みましたが、
clip 間のばらつきを超えたままです。

#### 全体値と内訳が食い違う（M5 と同じ形）

26 clip 全体では 0.4910 → 0.4981 と小さく見えますが、**分けると効果が明確です**。

| | 未知 source 20 | hold-out 6 |
|---|---:|---:|
| GAN 無し | 69.4% | 90.6% |
| **GAN 有り** | **75.3%** | **93.9%** |
| Seed-VC | 77.1% | 90.6% |

**未知 source では Seed-VC まで 1.8 点差、hold-out では上回りました。** 全体値が低く出るのは
平均の取り方（clip × 参照のペア単位）の違いで、**内訳のほうが実態を表します**。

**signal quality も改善しています**（stoi の上限との差 −0.019 → −0.008）。過平滑が減って、
自分のボコーダー上限にさらに近づいたということです。

#### この実験で言えること / 言えないこと

**言えること:** **過平滑が話者性の主因だった**という M5 の診断は正しく、GAN で実際に改善します
（未知 source 69.4% → 75.3%）。**trade-off も出ません**（内容 cos は微増、F0 相関は一定）。

**言えないこと:** **これで Seed-VC に並んだとは言えません。** guard rail は落ちたままで、
**blind listening test も Seed-VC 選好**でした（25 判定中 21、2026-09-13）。残る差の原因は、**未知話者への転移**に絞られています（hold-out では拮抗するため）。

**案 B（base から GAN 付きで学習し直す）は未実施**です。案 A で効果が確認できたので、
B に進む根拠はできましたが、**8〜12 時間の学習**になるため改めて判断が要ります
（**要ユーザー判断**）。

---

### 進捗（2026-09-02）: **GAN は効いた。過平滑が主因だったことの確認**

**確認済み:** RTX A4000 で 20,000 step の GAN fine-tune を実施しました。成果物は
`.m0data/gan/`（checkpoint 8 本 + 記録、**全 8 本の読み込みを確認してから破棄**）。

| 実測 | 値 |
|---|---|
| 速度 | **2.76 step/s** / 44.0 examples/s / 75,797 frames/s |
| 20,000 step の所要 | **121 分** |
| peak VRAM | **2.74 GB**（GAN 無しの 2.08 GB から +0.66 GB） |
| GPU 費用 | **約 $0.21** |

#### 結果（未知 source 20 clip、16 step、M5 と同じ test set）

| checkpoint | 話者 cos | 回復率 | 内容 cos | F0 相関 | 細部比 |
|---|---:|---:|---:|---:|---:|
| **GAN 無し**（M5） | 0.4910 | 55.3% | 0.8398 | 0.9995 | 1.099 |
| GAN 2,500 | 0.5519 | 70.4% | 0.8446 | 0.9996 | 1.083 |
| GAN 5,000 | 0.5603 | 72.5% | 0.8431 | 0.9996 | 1.284 |
| GAN 10,000 | 0.5550 | 71.2% | 0.8387 | 0.9996 | 1.354 |
| **GAN 15,000（採用）** | **0.5676** | **74.4%** | 0.8408 | 0.9996 | 1.389 |
| GAN 20,000 | 0.5607 | 72.6% | 0.8419 | 0.9996 | 1.462 |

**8 本すべてが事前登録した 3 条件を満たしました。** 規則どおり話者類似度が最大の
`ckpt_015000` を採ります。

**話者類似度が 0.4910 → 0.5676（回復率 55.3% → 74.4%）。** Seed-VC は 0.5912 なので、
**差 0.100 のうち 0.077 が埋まりました**（残り 0.024）。

#### 予想と違った点: trade-off が出ない

**M4 の fine-tune も `num_steps` の掃引も「話者性を上げると内容保持が落ちる」形**でしたが、
**GAN では内容 cos がむしろ上がりました**（0.8398 → 0.8408〜0.8446）。F0 相関も 0.9996 で
一定です。**過平滑の解消は、話者性と内容保持の両方に効く**ということです。

**これは原因診断の裏づけになります。** trade-off が出るのは「target への適合と汎化が
競合する」場合で、過平滑の解消はそれとは別の軸だった、と読めます。

#### 学習を進めても単調には良くならない

**2,500 step で既に 70.4%** に達し、そこから 20,000 step までは 70.2〜74.4% で**ほぼ平坦**です
（最良は 15,000）。**改善の大半は最初の 2,500 step で起きています。**

**細部比は単調に増え続けます**（1.083 → 1.462）。**しかし話者性は追随しません。**
`num_steps` の掃引と同じ形で、**細部の量は目的ではない**ことの再確認です。判定に使わない
と決めておいたのは正しかったことになります。

#### 測定の注意: clip 数で値が変わる

途中経過（8 clip）と最終（20 clip）で **0.017〜0.029 の差**が出ました。8 clip は test set の
先頭（女性 source 寄り）、20 clip は男女 11/9 です。**男性 source は異性変換で難しい**ため、
20 clip のほうが低く出ます。**同じ clip 構成の値どうしだけを比べること。**

---

### 事前登録した判定規則（**学習の前に書いた**）

**仮説:** GAN を入れると mel の細部が戻り、話者類似度が上がる。

| 項目 | 規則 |
|---|---|
| **主要な判定** | **未知 source の話者類似度**（M5 と同じ test set・同じ ECAPA・12 秒以上） |
| **成功の条件** | 話者類似度が **`ckpt_010000` + 16 step（0.4910）を上回る** |
| **制約 1** | 未知 source の**内容 cos が 0.02 を超えて落ちない**（M4・M5 と同じ値） |
| **制約 2** | **F0 相関が 0.99 を下回らない**（GAN は音程を壊すことがある。現状 0.9995） |
| **checkpoint の選び方** | 上の 3 つを満たすもののうち話者類似度が最大。**train loss で選ばない** |
| **失敗の判定** | 上記を満たす checkpoint が 1 つも無ければ **A は失敗**とし、B へ進むかを改めて判断する |

**細部比（ラプラシアン分散比）も記録します**が、**判定には使いません**。16 step の掃引で
**細部比が 1.0 を超えても話者性は頭打ちになる**ことが分かっており（8 step 以降 1.05〜1.13）、
**細部の量は目的ではない**からです。

**比較は `num_steps` を揃えて行います。** 既定の 16 step で比べ、1 step でも記録します
（GAN で 1 step 品質が改善するなら、それ自体が成果です）。

### 設定

SVS 側で実績のある `3singer_ritsu3style_uv_gan2d.yaml` の GAN 設定を土台にします
（`d_type: mel2d` / `cond: speaker` / `d_warmup_steps` と `gan_ramp_steps` で段階的に入れる）。
**`gan_start_step` は 0 にしません** - discriminator を暖機してから adversarial を
立ち上げる二段構成が SVS で機能しているためです。

## M5. offline 品質ゲート（Seed-VC 比較）

### 目的

**内部の loss ではなく外部の baseline に対して**、同一条件で品質を示します。ここを通過するまで、リアルタイム化の最適化を主目的にしません。

### ゴール

Gate B の全項目を満たすこと。

1. held-out song と未知 source singer の両方で変換できている。
2. 客観指標を記録してある: F0 correlation / RMSE / V-UV error、speaker similarity、CER、信号品質、timing、RTF と peak VRAM（特徴抽出と vocoder を含むか除くかを併記）。
3. Seed-VC と **blind listening test** を実施してある。system 名を隠し、順序を randomize し、loudness を揃えてある。評価者数・clip 数・除外規則を事前に決めてある。
4. failure sample を除外せず、[評価計画](svc-evaluation.md) の failure taxonomy で分類して残してある。
5. Seed-VC 側の revision、checkpoint、inference steps、F0 条件、reference clip を manifest に固定してある。default と高速設定を混同しない。

### 成果物

評価 report（[評価計画](svc-evaluation.md) 9 節のテンプレート準拠）、全評価 clip の manifest と出力、blind test の生データ。

### 前提・依存

M4 完了。

**M3 / M4 の実測から、比較条件そのものに注意が要ります（2026-09-01 追記）。**

1. **移調条件を両システムで揃えること。** LeapSVC の出力スペクトル傾斜は入力 F0 に強く従うため、
   男性 source → 女性 target では `--transpose +7〜+12` を使います。**Seed-VC 側の F0 条件
   （移調・自動シフトの有無）を manifest に固定し、同じ条件で並べること。** 片方だけ移調すると、
   モデルの優劣ではなく音域合わせの有無を比べることになります。**移調あり・なしの両方を
   報告するのが安全**です。
2. **音量の扱いを揃えること。** 持ち込み音源は学習分布より大きいため LeapSVC は
   `--match-loudness` が要ります（付けないと centroid が上限比 −47%）。**推論前に peak 正規化を
   しないこと**（学習は生の音量で特徴を取る）。Seed-VC 側の前処理も記録します。
   blind test 用の loudness 揃えは、**両システムの出力に同じ処理**で当てます。
3. **話者類似度は較正済みの条件でのみ測ること。** ECAPA-TDNN・**12 秒以上**のクリップ
   （[評価計画](svc-evaluation.md) 4 節の較正表）。6 秒では較正を通りません。
   **test set のクリップ長を 12 秒未満にしないこと**が設計上の制約になります。
4. **指標の道具は 4 つとも揃いました（2026-09-01）。** timing / CER / 信号品質 / 推論 RTF。
   ただし**それぞれに限界があり、M5 で読むときの前提になります**（[評価計画](svc-evaluation.md)
   4 節）。とくに **CER は `--language` を素材に合わせること**（VocalSet はイタリア語・英語・
   ラテン語で、`ja` を強制すると全滅します）、**timing のずれは分解能 5.8 ms 以下**なので
   `matched_ratio` を読むこと、**RTF の最大の項はボコーダー**（合計 0.654 のうち 0.355）で
   acoustic は 0.081 にすぎないこと。

### 進捗（2026-09-01）: **道具は揃った。測定本番は未実施**

**確認済み:** ゴール 2 が要求する客観指標のうち、道具が無かった 4 つを実装しました。
**追加の依存はありません**（`torchaudio` は `speechbrain` と一緒に、`transformers` は既存）。

| 指標 | 道具 | 実測で分かった限界 |
|---|---|---|
| timing | [`timing_metrics.py`](../tools/timing_metrics.py) | **分解能は hop（5.8 ms）。** M4 の 6 clip でずれの中央値がちょうど 1 フレームだった。読むべきは `matched_ratio`（**69.1%** = onset の 3 割は対応が付かない） |
| CER | [`asr_cer.py`](../tools/asr_cer.py) | **`--language` が素材と合わないと全滅する。** VocalSet に `ja` を当てて 3 clip とも CER 1.0。日本語素材では機能（上限 0.0 / 変換 0.60、n=1） |
| 信号品質 | [`signal_quality.py`](../tools/signal_quality.py) | **SQUIM は話し声で学習**。歌声への妥当性は未検証。上限との差のみ |
| 推論 RTF | [`rtf.py`](../tools/rtf.py) | **段別に出す。** CPU 実測で acoustic 0.081 / 合計 0.654、**最大の項はボコーダー 0.355** |

**RMS を揃えても、明るい音は大きく・近く聴こえます。** loudness を揃えたのは
「大きいほうを選ばないため」でしたが、**明るさは揃っていませんでした**。評価者自身の
言葉が「選んだほうが大きかった」なので、**選好は知覚的な大きさで決まっていた**ことに
なります。これは事前登録した基準（自然さ・こもり・破綻）とは違う軸です。

**それでも preference の結果は取り下げません。** 都合の悪い結果を後から無効にするのは、

記録するのは結果と交絡の両方です。

**分かったのは次の点です。**

> **選好されたほうが、target に近いとは限りません。** Seed-VC は target 本人の録音より
> **1.85 倍明るく**、LeapSVC は **target とほぼ同じ明るさ**です（1067 対 1160 Hz）。

**決定（2026-09-13）: target 忠実を採ります。** 明るくすれば選好は取れますが、
**target から離れます**。モデルの目標は「本人に似ていること」であり、聴いたときの
大きさはミックス段で扱う、という整理です。

**注意: レベルを上げても「小さく感じる」は直りません。** 原因は明るさ（スペクトル配分）
であってレベルではないので、フェーダーでは存在感が増えません。直すなら EQ ですが、
それは **target から離れる操作**です。**モデル側では明るさを足しません。**

**この決定の帰結:**

- **preference で Seed-VC に勝つことは目標ではなくなりました。** 明るさの差がある限り、
  知覚的な大きさで選好は動きます。
- 品質の判定は **target との距離**（話者類似度・帯域配分・F0・timing）で行います。
- **「Seed-VC より良い」は引き続き書けません**（blind で負けたという事実は残るため）。

**未検証:** 明るさを揃えた条件での blind は行っていません。そもそも明るさは
**評価対象そのもの**なので、揃えると何を比べているか分からなくなります。

uv run python tools/blind_test.py tally --sheet out/m5/blind/sheet.csv \
  --key out/m5/blind/key.json --out out/m5/blind/result.json
```

**参照音声を 2 つ添えます。** 「基準の音が無いと判断できない」という指摘によるものです。

| 参照 | 中身 | 系が漏れない理由 |
|---|---|---|
| target 本人の録音 | 波音リツの実録音 30 秒（加工なし） | どちらの系の出力でもない |
| そのペアの変換元 | 入力の歌 | **両系で同一の入力** |

**上限（`*_vocoder_only.wav`）は参照にできません。** 上限は **LeapSVC 自身のボコーダー
（NHVSing）の出力**なので、その癖を耳が覚えると **A / B のどちらが LeapSVC かを当てられます**。
`listen_page()` は上限のパスを渡されると落ちます（後から「正解を入れよう」として blind を
壊さないため）。参照は `context/` へ**中立な名前で複写**します — 元の場所を直接指すと
**パスに system 名が出ます**。

**確認済み（2026-09-13）: 結果は Seed-VC 選好です。** 26 ペアすべてに投票し、
**25 判定中 21 が Seed-VC、4 が LeapSVC、引き分け 1**（符号検定 p = 0.0009・参考値）。
**N=1 の非公式 preference test** であり、MOS ではありません。生データは
`out/m5/blind/{sheet.csv,key.json,result.json}`。

| 区分 | ペア数 | LeapSVC | Seed-VC | 引き分け |
|---|---:|---:|---:|---:|
| hold-out（target 本人の歌） | 6 | 2 | 3 | 1 |
| **未知 source** | 20 | **2** | **18** | 0 |

**差は未知 source に集中しています。** hold-out では拮抗しており、客観指標の傾向
（hold-out の回復率は LeapSVC 93.9% 対 90.6% で上、未知 source は 75.3% 対 77.1% で下）と
一致します。**自己再構成はできていて、未知話者への転移が弱い**という切り分けが、
主観でも裏づけられました。

**これで完了レベル 4 に到達しました。** レベル 4 は比較を**完了する**ことが条件で、
勝つことは条件ではありません。ただし **guard rail も preference も落ちているので、
「Seed-VC より良い」とは書けません**。

**集計時に票を失う不具合を踏みました（修正済み）。** `prepare` が書くヘッダは
`vote  # vote に A / B / tie を書く` で、`csv.DictReader` は 3 列目の名前を**説明ごと**
受け取ります。`row["vote"]` を引くと **26 票すべてが未記入**と読まれ、**例外は出ません**。
`read_sheet()` を足して `vote` で始まる列を採るようにし、票の列が無ければ落とすように
しました（黙って空を返すのが今回の壊れ方だったため）。**記入済みのシートを初めて通した
ときに初めて露出する**類の不具合です。

#### この比較の限界（読むときの前提）

- **Seed-VC は zero-shot、LeapSVC は target へ fine-tune 済み**です。条件は対等ではありません。
  reference は hold-out 曲から取り、学習曲を避けていますが、それでも非対称は残ります。
- **話者類似度の 1 値は 676 ペアの平均**で、内訳は女性 source 69.1% / 男性 source 53.8% /
  hold-out 22.1%（LeapSVC）。**平均だけを読まないこと。**
- **上限を共有できないため、CER と信号品質は 2 系で比べていません。** LeapSVC 側の
  「自分の上限からどれだけ落ちたか」だけを示しています。

### `num_steps` の掃引結果（2026-09-01）: **規則により 16 を選択**

**確認済み:** M5 の test set（未知 source 20 clip、GPU）で掃引しました。一次データは
`out/m5/steps_sweep.json`。

| steps | 話者 cos | 回復率 | 内容 cos | 1 step からの低下 | 細部比 | flow 秒 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 0.5055 | 58.9% | 0.8587 | - | 0.823 | 0.175 |
| 2 | 0.5110 | 60.2% | 0.8576 | +0.001 | 0.883 | 0.122 |
| 4 | 0.5243 | 63.5% | 0.8539 | +0.005 | 0.970 | 0.167 |
| 8 | 0.5372 | 66.8% | 0.8460 | +0.013 | 1.047 | 0.212 |
| **16（採用）** | **0.5444** | **68.6%** | 0.8398 | +0.019 | 1.099 | 0.371 |
| 32 | 0.5440 | 68.5% | 0.8338 | **+0.025**（制約外） | 1.128 | 0.594 |

**32 step は制約（内容 cos の低下 0.02 以内）を外れて脱落**しました。**しかも話者性が
伸びていません**（68.6% → 68.5%）。**規則が無くても 16 が頭打ち**だったことになります。

**回復率 58.9% → 68.6%（+9.7 点）。** Seed-VC は 0.5787 なので、**差 0.073 のうち 0.039 が
埋まりました**（残り 0.034）。

#### 予想と違った点

**細部比が 1.0 を超えます**（8 step 以降）。**GT より細かい**という意味で、単に「戻る」のでは
なく**行き過ぎ**ています。**話者性が 16 で頭打ちなのはこれと整合します** - 細部の量が
合っても、正しい細部とは限りません。**細部比 1.0 を目標にしないこと。**

**flow の所要は単調ではありません**（1 step 0.175 秒 > 2 step 0.122 秒）。呼び出しの
オーバーヘッドと GPU の暖機が支配的で、**16 step でも 1 step の 2.1 倍**にとどまります。

#### 反映したもの

**SVC 経路の既定を 16 にしました**（[`tools/svc_defaults.py`](../tools/svc_defaults.py) の
`SVC_NUM_STEPS`）。`infer_svc_mel` と `svc_convert` / `svc_batch` / `m3_verify` が参照します。

**SVS 経路（`infer_mel`）は触っていません。** 今回測ったのは SVC 経路だけで、**測っていない
経路の既定を変えない**ためです。README の「1-step」は SVS 経路の説明であり、変わりません。

### `num_steps` の選択規則（2026-09-01 登録。**掃引の前に書いた**）

**決定:** 話者性のために step を増やすと内容保持が落ちます（探索で 16 step のとき
内容 cos −0.017）。M4 と同じ形で、**先に規則を固定**します。

| 項目 | 規則 |
|---|---|
| **最大化するもの** | 未知 source の**話者類似度**（target への回復率） |
| **制約** | 未知 source の**内容 cos が 1 step から 0.02 を超えて落ちない**こと |
| **同点のとき** | **小さい step を採る**（速いほうが良い。RTF は小さいが 0 ではない） |
| **測る対象** | M5 の test set（未知 source 20 clip）。**hold-out で決めない**（自己再構成は簡単すぎる） |

**制約 0.02 は M4 で使った値と同じ**です（base からの許容低下）。**探索で見た数値に合わせて
決めたのではなく、既にある規則を流用**しています。

**この規則で決まらない場合**（すべて制約を満たす等）は、**飽和点**を採ります — 回復率の
増分が 1 点未満になった最初の step。細部比が 1.0 に近づけば頭打ちになるはずで、
それ以上は RTF を払うだけです。

### 話者性が弱い原因の調査（2026-09-01）: **過平滑。step を増やすと戻る**

**確認済み:** M5 で「話者類似度が Seed-VC に劣る」と分かったので、層ごとに切り分けました。
一次データは `out/m5/probe{1..6}_*.json`。

#### 層ごとの切り分け（自己再構成 = 全条件が target）

| 段 | リツへの回復率 | 読み方 |
|---|---:|---|
| ① source（リツ本人の録音） | 98.5% | 素材は正しい |
| ② 上限（GT mel → ボコーダー） | **96.4%** | **mel 表現とボコーダーは無罪**（−2 点しか落ちない） |
| ③ 変換出力 | **77.6%** | **音響モデルの中で 19 点失われる** |

**全条件が target でも 77.6% で頭打ち**でした。ここがモデルの天井です。

#### source 話者の漏れは無い

| | 対 target | 対 source 話者 |
|---|---:|---:|
| source そのもの | — | 0.8075 |
| **LeapSVC 変換** | 0.5129 | **0.2643** |
| Seed-VC 変換 | 0.5787 | 0.2151 |

**下限（0.2696）に張り付いています。** content / F0 / loudness から source 話者性は
漏れていません。**出力は「別人に似ている」のではなく「誰にも似ていない」**方向です。

#### 話者条件は効いている

同じ source を `spk_id` だけ変えて変換しました。

| spk_id | リツへの近さ | 回復率 |
|---|---:|---:|
| **22（target）** | **0.5161** | **61.5%** |
| 0 / 5 / 11 / 17 | 0.20〜0.28 | −18% 〜 +2% |

**target を指定したときだけ大きく寄ります**（可能な移動量の約 65%）。話者条件は弱くありません。

#### 原因: mel の細部が足りない（過平滑）

予測 mel を GT mel と直接比べました（自己再構成 6 clip）。

| 指標 | 値 |
|---|---|
| L1 | 0.477 |
| **ラプラシアン分散比** | **0.755** |

**細部が 25% 欠けています。** これは **flow 損失 + mel 再構成損失だけで学習した**ことの
典型的な帰結で、実際 **base（60,000 step）も fine-tune（20,000 step）も `gan.enabled: false`**
でした。**話者性を運ぶのは細部**（formant の鋭さ、倍音構造）なので、平滑化されると
「誰でもない声」になります。

#### 因果の確認: step を増やすと細部と話者性が**同時に**戻る

| steps | 細部比 | 話者 cos | 回復率（自己再構成） |
|---|---:|---:|---:|
| 1 | 0.755 | 0.5830 | 78.2% |
| 4 | 0.850 | 0.6060 | 84.0% |
| **16** | **0.957** | **0.6325** | **90.6%** |

**単調で、細部と話者性が連動しています。** 過平滑が原因であることの確認です。

**未知 source（実際の用途）でも効きます。** 内容保持のわずかな低下と引き換えです。

| steps | 話者 cos | 回復率 | 内容 cos |
|---|---:|---:|---:|
| 1 | 0.5054 | 58.8% | 0.8680 |
| 4 | 0.5259 | 63.9% | 0.8647 |
| **16** | **0.5477** | **69.4%** | 0.8515 |

Seed-VC は 0.5787。**差の大半が埋まります**（0.5054 → 0.5477）。

**費用はほぼ無視できます。** flow の RTF は 0.044 → 0.065（同一 run で測定）。**step を 16 倍に
しても 1.5 倍にしかならない**のは、大半が呼び出しのオーバーヘッドだからです。合計 RTF への
影響は +4.5% 程度です。

#### 以前の結論の訂正

**「60,000 step の base では 1 step と 16 step が実質同等」は、明るさ（spectral centroid）に
ついての話でした。** **細部と話者性では明確に差があります**（細部比 0.755 対 0.957、
回復率 78.2% 対 90.6%）。**測っていた量が違うだけで、当時の測定自体は誤っていません。**
「1 step で十分」を細部や話者性へ広げないこと。

#### 対処の候補

| 手 | 効果 | 費用 |
|---|---|---|
| **`--num-steps 16` で推論する** | 未知 source の回復率 58.8% → **69.4%** | RTF +4.5%、内容 cos −0.017。**再学習なし** |
| **GAN を有効にして学習** | 過平滑そのものへの対処（[条件付きトラック C](#c-gan-の導入)） | 再学習が要る。**base からやり直し** |

**推奨:** まず `--num-steps` の既定を見直します（再学習なしで効く）。GAN は M6 の前に
検討する価値がありますが、base の作り直しになるため費用が大きく、**先に num_steps で
どこまで届くかを測ってから**判断します。

### 事前登録した判定規則（2026-09-01 決定。**測定の前に書いた**）

**決定:** M4 で「規則を後から決めると train loss で選んでしまう」ことが実証されたので、
M5 でも**測定より先に**規則を固定します。以下は結果を見る前の決定です。

#### 決定 1: 判定は guard rail 方式にする

**絶対的な数値閾値は置きません。** 手元のデータは CER が n=1、信号品質が n=2 で、
SQUIM の `si_sdr` は 2 clip で符号が反転しています（−2.779 と +1.387）。**この数から閾値を
作ると、根拠のない数を発明することになります。**

| 役割 | 内容 |
|---|---|
| **主要な判定** | **blind preference**（M5 の目的が比較だから） |
| **guard rail** | content cos / 話者類似度の回復率 / F0 相関 / timing の対応率 の **4 つ** |
| **「悪化」の定義** | **clip 間のばらつき（標準誤差）を超えて Seed-VC より低いこと**。任意の数字を発明しない |
| **主張の制限** | **preference で勝っても guard rail を 1 つでも落としていたら「より良い」とは書かない。** 「preferred だが X は低い」と両方書く |

guard rail の 4 つは**すべて source か target 録音を基準**にしており（下記の決定 3）、
Seed-VC の出力にもそのまま当てられます。

#### 決定 2: 主観評価は N=1 の非公式 preference test

**確定:** 評価者は**開発者 1 名**です。

- **「非公式・N=1 の blind preference」と明記し、MOS とは呼びません。**
- blind の条件（ラベルを隠す・順序を randomize・両システムに**同じ**loudness 揃えを当てる）は
  満たすので、[主張ルール](svc-prior-art-license.md) 6 節の「同一 test set の blind comparison」は
  満たせます。**ただし N=1 を必ず併記します。**
- **除外規則は先に決めます:** 技術的失敗（無音・NaN・長さ不一致）**のみ**除外。
  「気に入らない」で外さない。除外した clip は理由付きで残します。

#### 決定 3: 上限は共有しません（技術的に不要）

**確認済み:** 比較に使う指標は**ほぼ全部 source か target 録音を基準**にしており、
系をまたいでそのまま並べられます。**上限を共有する必要はありません。**

| 指標 | 基準 | 系をまたげるか |
|---|---|---|
| content cos | **source** の ContentVec 特徴 | ✓ 同じ encoder・同じ source なら |
| 話者類似度 | **target 歌手の録音**（上限も下限も） | ✓ ボコーダーに依存しない |
| F0 相関 / 半音誤差 | **source** の F0 | ✓ |
| timing | **source** の onset | ✓ |
| CER | **source** の書き起こし | ✓ 同じ ASR なら |
| 信号品質（SQUIM） | 参照不要の絶対値 | ✓ |
| RTF | — | ✓ 同じ機種で測れば |
| **上限（GT mel → 自分のボコーダー）** | **自分の系** | ✗ 系が違う |

**上限は「自分の系の中でどこまで到達したか」を診断する脚注**であって、比較の軸ではありません。
各システムが自分の上限を脚注として持てば済みます。

#### 決定 4: test set は 20 clip

| 条件 | 値 | 理由 |
|---|---|---|
| clip 数 | **20** | M3 の測り直しで 20 clip では偏りが出たが、そこは**素材の選び方**（`rglob` の並び順で 18 女性 / 2 男性になった）が原因。**構成を明示的に決める**ことで対処する |
| 長さ | **12 秒以上** | 話者類似度の較正がその長さでしか通らない |
| 言語 | **日本語を必ず含む** | CER は言語が合わないと全滅する |
| 性別 | **同性・異性の両方** | 回復率の伸びが倍違う（同性 +17.4 点 / 異性 +8.4 点） |
| 素材 | **held-out song と未知 source singer の両方** | ゴール 1 の要求 |
| 移調 | **male source → female target は +7〜+12 半音**。両システムで同じ条件 | 出力の傾斜が F0 に強く従う |



### 測定の手順（2026-09-01 に道具を揃えた）

**確認済み:** 客観指標の道具は揃っています。**ただしバラバラに走らせると条件が揃わない**ので、
次の順で回します。**上限（`*_vocoder_only.wav`）を作る `--self-check` を省かないこと** —
CER と信号品質は上限が無ければ実行を拒否します。

# 3. 話者類似度。**12 秒以上のクリップで**

  --target download/ritsu --unrelated .m0data/unrelated_ref --seconds 20

# 4. M5 で追加した 4 つ
uv run python tools/timing_metrics.py  --dir out/<run> --out out/<run>/timing.json
uv run python tools/asr_cer.py         --dir out/<run> --language ja --out out/<run>/cer.json
uv run python tools/signal_quality.py  --dir out/<run> --out out/<run>/sq.json
uv run python tools/rtf.py --wav <vocal.wav> --ckpt <ckpt> --manifest <manifest> \
  --out out/<run>/rtf.json
```

**test set の設計に効く制約（道具の側から決まるもの）:**

| 制約 | 理由 |
|---|---|
| **クリップは 12 秒以上** | 話者類似度の較正がその長さでしか通らない |
| **日本語の素材を入れる** | CER は言語が合わないと全滅する。VocalSet（伊・英・羅）だけでは測れない |
| **上限を必ず作る** | CER・信号品質・明るさは上限との差でしか読めない |
| **移調条件を固定して記録** | 明るさが F0 に強く従う。両システムで揃えないと不公平 |

**Seed-VC 側にも同じ 4 指標を当てられます**（どれも WAV のディレクトリを受け取るだけで、
LeapSVC の内部に依存しません）。**ただし上限の作り方は揃えること** — Seed-VC は mel 表現も
ボコーダーも違うので、「GT mel の再合成」は同じ意味になりません。**共通の上限を使うか、
上限に依存しない指標（timing・話者類似度）で比べるか**を、比較の前に決めます（**要ユーザー判断**）。

### 主張の制約

**決定:** 「Seed-VC より良い」という表現は、このマイルストーンの blind comparison を経た後にのみ使います。ここを通過して初めて完了レベル 4 到達です。

**注意:** Seed-VC は GPL-3.0 です。外部 baseline として実行するだけとし、コードをこのリポジトリへ取り込みません。比較 script と manifest は独立に管理します。

### 要ユーザー判断 -> 決着

~~合格とする最小差、評価者数、対象楽曲の閾値は、test set 作成後に確定します。~~

**決着（2026-09-01 に登録 / 2026-09-13 に実施）:**

| 項目 | 決着 |
|---|---|
| 合格とする最小差 | **guard rail 方式**（clip 間のばらつきを超えた悪化を NG）。**測定の前に**登録した |
| 評価者数 | **N=1 の非公式 preference test**。MOS とは呼ばない |
| 対象楽曲の閾値 | 12 秒以上・**有声率 60% 以上**・日本語を含む・同性 / 異性の両方 |
| 上限の共有 | **しない。** 上限に依存する指標（CER・信号品質・明るさ）は 2 系で比べない |
| **明るさをどうするか** | **target 忠実を採る（2026-09-13 決定）。** モデル側で明るさを足さない |

**残っている判断は [2b 節](#2b-ここからの計画) の①（類似の blind を実施するか）と
②（案 B へ進むか）です。**

## M6. streaming student

**条件付き（2026-09-14 決定）。直列経路から外しました。must ではありません。**

### 起動条件（2026-09-14 決定）

**SVC の品質が十分になってから着手します。** ただし「十分」を言葉のままにすると**発火しない
条件**になるので、測れる形にしておきます。

| | 条件 | 備考 |
|---|---|---|
| **1** | 同一 test set の blind comparison で **preference が baseline を上回る** | M5 で事前登録した `may_claim_better` の条件そのもの |
| **2** | **guard rail を 1 つも落としていない** | 同上 |

**推奨（要ユーザー判断）: 比較対象を Seed-VC だけにしないこと。** 現在の外部 baseline は
**Seed-VC 1 系だけ**です。品質の到達点を外部基準で言うなら、**比較対象を広げる必要が
あります**（RVC / So-VITS-SVC / [Beatrice](https://prj-beatrice.com) など）。Beatrice は
同じ手元で動いており、**話者類似度の到達率 93.8%** という値も取ってあります。**どこまでを
比較対象にするかは決めていません。**

**文書に書く言葉について。** 目標として「SOTA」を置くのは明確ですが、**文書と README には
そのまま書きません**。[主張ルール](svc-prior-art-license.md) 6 節に従い、**軸と比較対象と
test set を明示した記述**に置き換えます（「世界初」「唯一」を使わないのと同じ理由です）。

### 目的

offline teacher は phrase 全体を見る non-causal モデルです。実時間で使うには未来の文脈を削る必要があり、その劣化を蒸留で最小化します。

### ゴール

Gate C の全項目を満たすこと。

1. teacher と**同じ test set**で student を評価し、品質低下と遅延改善を同時に報告してある。
2. chunk 境界に click、音切れ、F0 jump がない。
3. 実機で測定してある: RTF、algorithmic lookahead、そして audio I/O を含む **end-to-end latency**。内訳（input buffer / SSL encoder の receptive field / pitch extractor の lookahead / student の lookahead / vocoder の overlap / output buffer）を分解して記録する。
4. 長時間連続運転で buffer overrun / underrun が発生しない。

### 成果物

student checkpoint、遅延内訳表、連続運転ログ、teacher との比較 report。

### 前提・依存

M5 通過。**決定:** M5 を通過していない teacher を基準に student を作りません。
**さらに 2026-09-14 の決定により、上の起動条件を満たすまで着手しません。**

**確認済み（2026-09-01、M5 の RTF 測定）: 最初の作業は蒸留ではありません。** GPU の
end-to-end RTF 0.464 のうち **ボコーダーが 0.432（93%）** で、acoustic は 0.006 です。
**蒸留は lookahead（遅延）に効き、RTF（処理量）には効きません。** 詳細と進め方は
[2b 節](#2b-ここからの計画) の④。

| 段 | 手 |
|---|---|
| **ボコーダー（RTF の 93%）** | 実行経路の選択（ONNX の EP、chunk 分割と overlap）。**M6 の最初の測定対象** |
| **acoustic（RTF の 1%）** | 因果化と蒸留。**lookahead を削るため**であって速度のためではない |
| content / F0 | streaming では 1 回あたりの窓が変わる。**per-chunk で測り直しが要る**（未測定） |

### 主張の制約

**決定:** 「リアルタイム」は、対象ハードウェアでの end-to-end latency 実測と連続動作の確認後にのみ使います。model の RTF 単体では根拠になりません。README 記載の RTF 0.027 は既存 **SVS 音響モデル**の値であり、SVC の特徴抽出・ボコーダー・ストリーミング I/O を含みません。

### 要ユーザー判断

許容する lookahead と往復遅延、音質と遅延のどちらを優先するか。

## 7. 条件付きトラック

直列経路には入れず、条件が成立したときだけ実施します。

### (A) SVS → SVC warm-start

**目的:** 既存 SVS checkpoint の flow backbone と励起を再利用し、M3 の学習コストを下げられるかを確認する。

**ゴール:** 部分 weight mapping と missing/unexpected key の allowlist を持つ loader、ロード結果の記録、そして**独立初期化した baseline との比較結果**。速度・品質の利得が示せない場合は採用しません。

**成果物:** 部分ロード対応の loader、load report、warm-start あり/なしの checkpoint 2 本と比較結果。

**前提:** M2 完了。**未実装:** 現在の `--init_from --finetune` は同一構造の checkpoint を前提としており、SVS→SVC の部分ロードには使えません。

**実施条件:** M3 の学習コストが問題になった場合のみ。再利用できるのは flow backbone・励起・損失・discriminator・NHVSing interface で、phoneme embedding・length regulation・phoneme encoder の入力 projection は再利用できません。

### (B) NHVSing target fine-tune

**目的:** vocoder 側に起因する artifact を切り分けて解消する。

**ゴール:** ground-truth mel を入力しても同じ artifact が出ることを示したうえで、fine-tune 前後を比較した結果。

**実施条件:** 次の 3 つがすべて成立したときのみ実施します。

1. target singer の高音や裏声で vocoder artifact が系統的に出る。
2. ground-truth mel を入力しても同じ artifact が出る。
3. 音響モデルの誤差と vocoder の誤差を切り分けられている。

**現状（2026-08-30）: 起動条件は成立していません。** M0 ゴール 4 の実測で、base 候補の
GTSinger は NHVSing 既知コーパスと同水準の再合成忠実度を示しました（[台帳 7b
節](svc-dataset-ledger.md#7b-nhvsing-にとって-in-distribution-かの実測2026-08-30)）。
M2 でも ground-truth mel 経由と予測 mel 経由がほぼ同等でした。**既存重みをそのまま使います。**

**追記（2026-09-13）: 上流が V3.1 へ差し替わりました**（倍音のにじみと高域の縞を修正）。
同じ checkpoint・同じ 26 clip で測り直しましたが、**追跡している指標では改善は出ていません**
（上限自身も動くため。M5 の該当節）。**起動条件は依然として成立していません。**

**成果物:** fine-tune 前後の vocoder 重み、同一 mel を通した比較サンプル、artifact の切り分け記録。

**前提:** M4 完了。まず既存重みを固定した baseline を作ってから比較します。**注意:** mel 分布への過適合、データ規約、重み配布条件を別途確認します。NHVSing V3 の配布重みは非商用データセットで学習されています。

### (C) GAN の導入

**目的:** flow 損失と再構成損失だけで学習した mel は平滑になりがちで、子音や息の質感が鈍ります。GAN はこれを鮮明化する後段です。一方で学習を不安定にし得るため、土台が固まる前に入れると「品質が悪いのは音響モデルか GAN か」を切り分けられなくなります。**土台の完成後に、別 run で**入れるのが目的です。

**ゴール:** 次の 3 つが揃った状態を完了とします。

1. GAN なし baseline と**同一の split・seed・更新 budget**で A/B 比較してある。
2. 客観指標と失敗分類の両方で改善が示せている（片方だけの改善は採用理由にしない）。
3. 悪化した run も残してある。GAN は不安定化させ得るので、失敗の条件自体が知見になります。

**成果物:** GAN あり/なしの checkpoint 2 本、A/B の指標と試聴結果、失敗分類。

**前提:** flow + 再構成が安定し、artifact を分類できていること。

**確認済み（2026-08-30、M3 の後）: 起動の根拠は揃いました。**

| 起動条件 | 状態 |
|---|---|
| flow + 再構成が安定している | 済。30,000 step 完走、eval loss 単調減少 |
| **artifact を分類できている** | 済。**高域不足**として特定（bin 80 以上が −0.15〜−0.19 ln-mel、centroid が上限比 −4〜−26%）。ボコーダー由来でないことも切り分け済み |
| 過平滑の兆候 | `laplacian_var_ratio` **0.869**（1.0 未満＝潰れ気味） |

**ただし「M4 完了後」という当初の前提より前倒しになります。** 高域不足が M4 の
fine-tune で軽くなる可能性があるため、**先に学習の継続（M3「M3 の後の分岐」の①）を試し、
それでも残るなら GAN**、という順序を推奨します。GAN を先に入れると「学習不足だったのか
GAN が効いたのか」を切り分けられません。

**実施条件:** 上記が成立してから、**別 run** で導入します。既存 SVS と同様に `gan_start_step` 以降の二段構成とします。baseline checkpoint は上書きしません。

**注意:** GAN 経路（`_forward_flow_gan`）は `compute_loss` と数式・mask・RNG 順を一致させて再実装されています。片方だけ変更すると学習が一致しなくなります。

**実施済み（2026-09-01 起動 / 2026-09-02 完了、案 A）。** 結果は本文書の
「条件付きトラック (C') GAN fine-tune」節にあります。**未知 source の回復率 69.4% → 75.3%、
trade-off なし**で、**過平滑が主因だったことの確認**になりました。**案 B（base から学習し直す）は
未実施**です（[2b 節](#2b-ここからの計画) の②。**要ユーザー判断**）。

## 9. 進行ルール

- **飛ばさない。** M1 を経ずに M3 以降は実行できません（shard がないため物理的に不可能）。M5 を経ずに M6 を主目的にしません。
- **上書きしない。** base checkpoint と fine-tune 成果物は別 `run_name` / 別ディレクトリに保存します。同じ `--run_name` で再実行すると `log/<run_name>/ckpt_*.pt` の最新から自動再開するため、別実験では必ず run 名を変えます。
- **テストを先に書く。** このリポジトリの実装はすべて TDD で行います。失敗するテストを書き、失敗を確認し、通す最小限のコードを書く。先に書いたテストが無い実装コードは破棄してやり直します（`superpowers:test-driven-development` と `leapsinger-tdd`）。
- **1 度に 1 要素。** ablation では同一 split・seed・更新 budget を使い、複数要素を同時に変えません。
- **環境を固定する。** Python 3.13 と `uv.lock` を実験の一部として扱い、torch / CUDA / 依存を更新した run はその差分を実験記録に残します。環境差による品質差はモデル差と見分けがつきません。
- **失敗を消さない。** failure clip は削除せず、category と suspected component を付けて残します。
- **完了を宣言する条件。** 各マイルストーンは、コードの存在ではなくゴール節の判定材料が揃った時点で完了とします。完了時に [`svc-implementation-status.md`](svc-implementation-status.md) の検証済み / 未検証境界と [`svc.md`](svc.md) の完了レベルを同時に更新します。
- **主張の範囲。** [先行研究・ライセンス・リスク](svc-prior-art-license.md) 6 節の主張ルールに従います。「世界初」「唯一」は使いません。「1-step」は acoustic flow の step 数であり、pipeline 全体の話ではありません。
- **測定コードは、本物の入力を一度通すまで信じない。** M5 では測定バグを 3 件踏み、**3 件とも
  例外を出さずにもっともらしい数値を返しました**（上限の混入・移調の未適用・CSV 列名）。
  **同じ量を 2 経路で測って食い違っていたら、どちらかが壊れています。**
  当て方は [leapsinger-tdd](../.claude/skills/leapsinger-tdd/SKILL.md) の 3b 節。
- **否定的な結果を残す。** 聴こえた defect が客観指標で再現しなかったとき、指標を取り替え続けると
  **結果に合う指標を選ぶ**ことになります。そのまま残し、次は評価者に聞き直します。
- **交絡は後から無効化しない。** blind が明るさの差の上で行われていたと分かっても、**選好の結果は
  取り下げません**。事前登録の規律が壊れるためです。足せるのは**別の質問**だけです。

## 10. ボコーダー V3.2 への移行判定（2026-09-18 **測定の前に登録**）

**発端:** 2026-09-18 に `main` へ merge した上流の `66b464e` が NHVSing を **V3.2** に
差し替えました（V3.1 を削除するもので、SVC 側の既定を保つために V3.1 を同梱へ戻しました）。
V3.2 が直したのは「**高音域でフレーム単位に波形が急激に弱まる**現象」で、LTV フィルタの
矩形 overlap-add によって、あるフレームの漏れ出しが逆位相で 1 周期を打ち消していたものを
**Hann WOLA（50% overlap）**に置き換えたものです。**入出力の仕様は V3.1 と同一**です。

**仮説:** これが 2026-09-13 の聴取で **6 本中 5 本が申告した「音量が揺れる」**の原因である。

### 先に確かめた事実（測定の前）

- **申告された 6 本はすべて LeapSVC 側**でした（`out/m5/blind/key.json` と `defects.csv` を
  照合。5 本が「音量が揺れる」、1 本が「音程が揺れる」）。
- **「申告なし」を対照群に使えません。** `defects.csv` に注記があるのは 6 本だけで、
  残り 20 本は**未判定**です（申告されなかったのではありません）。
- 申告された 5 本の出力 F0 中央値は **328 Hz**、未判定の unseen 15 本は **386 Hz** で、
  **高音ほど申告されているという関係にはありません**（最高音 649 Hz の clip は未判定）。
  **上流の「高音域で起きる」という説明を、この聴取の結果では裏づけられません。**
  ただし hop 256 / 44.1 kHz では 1 フレームが 5.8 ms なので、330 Hz でも 1 フレームに
  約 2 周期入ります ―― **どちらの群も上流が言う regime の中にあります**。

### 設計

- **acoustic は同一にします。** 同じ checkpoint（GAN `ckpt_015000`）・同じ manifest・
  16 step・同じ clip・同じ移調で、**CPU で回します**（CPU は bit 一致するので mel が完全に
  同じになり、**違うのはボコーダーだけ**になります）。
- **3 つの run:** `V3.1(a)`（既存 `out/m5/leapsvc_gan_v31`）、`V3.1(b)`（新規・ノイズ測定用）、
  `V3.2`（新規）。**NHVSing は seed の無い乱数を持つ**ので、同じ V3.1 を 2 回回した差が
  **run 間ノイズ**です。**閾値はこのノイズを実測してから立てます。**
- **主指標は `residual_db_std` と `fast_db_std`**（`tools/loudness_stability.py`）。
  **source を基準にするので上限が要らず、ボコーダーをまたいで比べられます。**
- **`fast_db_std` は 2 Hz より速い成分すべて**なので、per-frame の欠損には鈍いおそれが
  あります。**フレーム間差の標準偏差**（`frame_jitter_db`）を足して per-frame に絞った量も
  見ます（**先にテストを書いてから実装**します）。

### 判定規則（**この節を書いた後に測る**）

1. **V3.2 が「音量の揺れ」を直したと言えるのは**、26 clip の対応のある差
   `V3.1(a) -> V3.2` が同じ clip の `|V3.1(a) -> V3.1(b)|`（ノイズ）より大きく、かつ
   **符号検定で過半が改善側**のときだけです。**中央値だけを見ません。**
2. **上限どうしも比べます。** 同じ GT mel を V3.1 と V3.2 に通した `*_vocoder_only.wav` の
   CER と `fast_db_std` は、**ボコーダーそのものの比較**として正当です（系の比較ではない）。
3. **CER・信号品質・明るさの「上限との差」は、V3.1 と V3.2 でそれぞれ自分の上限に対して
   出します。** 2 つの差を比べるのは「acoustic の相対的な劣化が変わったか」であって
   **絶対品質の比較ではありません。** CER は離散で不安定なので、**これで既定を決めません**。
4. **既定を V3.2 に変えるのは**、(1) が成立し、かつ**上限の要らない指標**（話者類似度・
   timing・F0 / V-UV）が悪化しないときだけです。成立しなければ **V3.1 据え置き**とし、
   **否定的な結果をそのまま残します**。
5. **既定を変える場合は、README と doc の「上限との差」をすべて V3.2 で測り直します。**
   混ぜません。

### 予測（外れたら残す）

- V3.2 のほうが `fast_db_std` と `frame_jitter_db` が小さくなる。
- 差は **F0 が高い clip で大きい**（上流の説明が正しければ）。**ただし聴取の申告は高音に
  偏っていません** ―― この 2 つが食い違ったままなら、**「V3.2 は defect を直すが、聴取で
  名前が付いたものとは別物」**という結論になります。

### 結果（2026-09-18 実測）: **仮説は支持されませんでした。V3.1 据え置き**

**確認済み。** 一次データは `out/m5/_v32/loudness_compare.json`、run は
`out/m5/{v31_cpu_a,v31_cpu_b,v32_cpu}`（各 26 clip・CPU・GAN `ckpt_015000`・16 step）。

**設計の逸脱を 1 つ記録します。** 事前登録では V3.1(a) に既存の
`out/m5/leapsvc_gan_v31` を使うと書きましたが、**この run は `device: cuda`** でした。
CUDA は bit 再現しないので mel が一致せず、「違いはボコーダーだけ」になりません。
**V3.1(a) も CPU で取り直しました**（3 run すべて CPU）。

#### 上限どうし（同じ GT mel を 2 つのボコーダーに通す。**defect の直接の検証**）

| 量 | V3.1(a) | V3.1(b) | V3.2 | 差の中央値 | ノイズ | 改善した clip | p（符号検定） |
|---|---:|---:|---:|---:|---:|---:|---:|
| `residual_db_std` | 2.040 | 2.063 | 2.108 | **+0.068** | 0.016 | 8/26 | 0.0755 |
| `fast_db_std` | 1.313 | 1.309 | 1.280 | **+0.023** | 0.016 | 10/26 | 0.3269 |
| `frame_jitter_db` | 0.845 | 0.847 | 0.878 | **+0.035** | 0.021 | **6/26** | **0.0094** |

#### 変換結果（acoustic + ボコーダー）

| 量 | V3.1(a) | V3.2 | 差の中央値 | ノイズ | 改善した clip | p |
|---|---:|---:|---:|---:|---:|---:|
| `residual_db_std` | 1.897 | 1.945 | +0.010 | 0.023 | 11/26 | 0.5572 |
| `fast_db_std` | 1.371 | 1.431 | +0.027 | 0.022 | 10/26 | 0.3269 |
| `frame_jitter_db` | 0.868 | 0.908 | +0.007 | 0.011 | 10/26 | 0.3269 |

#### 判定

- **規則 1 は成立しません。** 改善側が過半になった量は 1 つもなく、`frame_jitter_db`
  （上限）は **6/26・p = 0.0094 で有意に悪化**しています。**規則 4 により V3.1 据え置き**です。
- **効果は有意でも無視できる大きさです。** 0.845 dB に対して +0.035 dB（4%）で、
  run 間ノイズ 0.021 dB の 1.7 倍しかありません。**「V3.2 のほうが揺れる」と読むべきでは
  ありません** ―― 読めるのは「**この測定では差が無い**」です。
- **申告された 5 本でも改善しません**（上限 `fast_db_std` 0.952 -> 1.007、
  `frame_jitter_db` 0.707 -> 0.752）。
- **予測「差は F0 が高い clip で大きい」も外れました**（Spearman rho は −0.221 〜 +0.045、
  いずれも p > 0.2）。事前に書いたとおり、**「V3.2 は defect を直すが、聴取で名前が付いた
  ものとは別物」**という結論になります。
- **規則 2（上限どうしの CER）は回していません。** 規則 1 が落ちた時点で既定は動かないので、
  156 本の書き起こしを回す理由が無くなりました。移行を再検討するときに回します。

#### この測定で分かった限界

- **3 つの量はどれも全フレームの std** なので、**欠損が疎だと薄まります**。上流が直したのは
  「あるフレームの漏れ出しが逆位相で 1 周期を打ち消す」現象で、**330 Hz の 1 周期は 3 ms、
  測定窓は 11.6 ms** です。1 回の打ち消しは約 −1.3 dB としてフレームに出るので測定は
  盲ではありませんが、**頻度が低ければ std には現れません**。
- **ここで指標を足しません。** 実データを見てから選ぶと、結果に合う指標を選ぶことに
  なります（M5 で踏んだ失敗）。`frame_jitter_db` は**データを見る前に**確定させました。
- **聴き直しは行いません（2026-09-18 に取り下げ）。** 素材は
  `out/m5/blind_wobble/`（29 ペア + catch trial 3）に用意しましたが、**結果で変わるものが
  ありません** ―― 既定（V3.1 据え置き）もコードも主張も動きません。**判断が懸かっていない
  聴取は回さないこと。**
  「否定的な結果はそのまま残し、次は評価者に聞き直す」という規則は、**defect の説明が
  必要なとき**のためのものです。ここでは候補の説明（V3.2）が既に否定されており、
  **聴いても出力は変わりません**。`blind_test.py` の `wobble` は残してありますが、
  **回すなら「この結果で何を変えるか」を先に書くこと。**
- **2026-09-13 に報告された「音量が揺れる」は未説明のままです。** 客観指標では LeapSVC の
  ほうが source に忠実で（残差 2.12 対 4.67 dB）、V3.2 でも動きません。読み方は 2 つ
  （**評価者のラベルが不正確だった**／**指標が捉えられない defect がある**）で、**決めるには
  評価者に聞き直すしかありません**。**ただし、どちらであっても出荷物は変わりません。**

#### 副産物: 「中央値の差」と「差の中央値」が実際に符号ごと食い違いました

上限の `fast_db_std` は **中央値の差が −0.032（改善）**、**差の中央値が +0.023（悪化）**です。
**同じデータで符号が逆になります。** 比較には**差の中央値**を使う、という規則
（[CLAUDE.md](../CLAUDE.md)）がここで効きました。

## 11. 男声・未知話者での移調の測り直し（2026-09-18 **測定の前に登録**）

**発端:** 低い声からの移調の既定 **+7 半音**（`SVC_TRANSPOSE_LOW_VOICE`）は、**日本語 8 clip・
1 話者・1 target** の掃引で決めました。文書自身が「**別の声では測り直すこと**」と書いています。
一方 **M5 の男声 10 本（VocalSet）は旧既定の +12 で測ったまま**で、README と doc に載っている
男声の数値はすべて +12 のものです。**+12 は日本語では両方の軸で劣る**と分かっているので、
男声でも同じ向きなのかを確かめます。

### 設計

- clip は **VocalSet の男声 11 本**（`unseen00` 〜 `unseen19` のうち `gender: male`。すべて
  **base に入っていない未知話者**）。target は波音リツ。
  **この節を書いた時点では「10 本」と書いていました** ―― 数える前に書いたためです。
  `testset.json` を数えて **11 本**（男声 11 / 女声 9）に直しました。
- **+7 の run を新しく作り、既存の +12（`out/m5/v31_cpu_a`）と対にして比べます。**
  checkpoint（GAN `ckpt_015000`）・manifest・16 step・V3.1・CPU はすべて同じで、
  **違うのは `--transpose` だけ**です。
- **run 間ノイズは `v31_cpu_b`（+12 の 2 回目）から採ります。** 同じ条件を 2 回回した差です。

### 指標と、なぜそれを選ぶか

- **主指標は話者類似度の回復率**（ECAPA-TDNN、20 秒）。**target 録音を基準にするので上限が
  要らず、移調をまたいで比べられます。**
- **明るさは「target 本人の録音（centroid 1160 Hz）からの距離」で見ます。** 上限
  （`*_vocoder_only.wav`）は**移調後の f0 で作られる**ので、+7 と +12 で上限自体が動きます。
  **上限比では移調をまたげません。**
- **CER は主指標にしません。** VocalSet はラテン語・イタリア語・英語で、**ラテン語は上限自身が
  23% 揃いません**。`cer_breakdown.py` で言語別に割り、読める群だけ参考にします。

### 判定規則（**この節を書いた後に測る**）

1. **男声でも +7 を既定にできる**と言えるのは、**回復率の対応のある差（+12 -> +7）が
   run 間ノイズより大きく、符号検定で 10 clip の過半が改善側**のときだけです。
2. **明るさが target から遠ざかったら、回復率が上がっても採用しません**（明るくすれば
   選好は取れるが target から離れる、という 2026-09-13 の決定）。
3. **どちらとも言えない場合は、既定を変えません**（`SVC_TRANSPOSE_LOW_VOICE` は日本語で
   決めた値のまま）。**そのときは「男声では確かめられなかった」と書きます。**
4. n=10・1 target なので、**結果がどちらでも「男声一般」には広げません。**

### 予測（外れたら残す）

- **+7 のほうが回復率が高い**（日本語と同じ向き）。
- ただし **VocalSet の男声は日本語の低音話者よりさらに低い**可能性があり、**F0 の一致には
  より大きな移調が要る**ので、**+12 が勝つ余地があります**。**話者類似度は単純な F0 の一致では
  決まっていない**（+9.7 半音の理論値より +7 が良かった）ので、予測の確度は低いままです。

### 結果（2026-09-18 実測）: **+7 は男声へ広げられません。男声では +12 のほうが良い**

**確認済み。** 一次データは `out/m5/_tr7/male_transpose.json` と
`out/m5/_tr7/male_brightness.json`、run は `out/m5/tr7_male`（+7）と
`out/m5/_tr7/tr12_male_{a,b}`（+12 を 2 回。b は run 間ノイズ用）。**11 clip、
違うのは `--transpose` だけ**です（GAN `ckpt_015000` / 16 step / V3.1 / CPU）。

#### 話者類似度（上限が要らない指標。ECAPA-TDNN、20 秒）

| 条件 | 回復率の中央値 |
|---|---:|
| +7 | 73.7% |
| +12（1 回目） | 70.7% |
| +12（2 回目） | 70.9% |

**中央値だけ見ると +7 が 3.0 点良く見えますが、対応のある差の中央値は −0.29 点**です。
**改善は 5/11（p = 1.0000）**で、**差はありません**。

#### 明るさ（target 本人の録音からの距離。**上限比では移調をまたげない**ため）

| 条件 | centroid の中央値 | target（1177 Hz）との差 | 距離の中央値 |
|---|---:|---:|---:|
| **+7** | 845 Hz | **−332 Hz** | **332 Hz** |
| +12 | 1190 Hz | +13 Hz | **145 Hz** |

**+12 は target の明るさとほぼ一致します**（差 13 Hz）。**+7 が target に近いのは 2/11 clip**
だけで、run 間ノイズは 2.0 Hz です。

#### 判定

- **規則 1 は成立しません**（回復率の改善が過半にならない）。**規則 2 に触れます**
  （+7 は明るさが target から遠ざかる）。**規則 3 により既定は変えません。**
- したがって **`SVC_TRANSPOSE_LOW_VOICE = 7` は日本語の低音話者で確かめた値のままで、
  男声（VocalSet）には当てはまりません。** M5 の男声の数値は +12 で取ってありますが、
  **その選択は結果的に正しかった**ことになります。
- **規則 4 のとおり「男声一般」には広げません**（n=11・1 target）。

#### 分かったこと: **必要な移調量は source の F0 に依る**

日本語の低音話者（夏目）では **+7 が +12 より良く**（回復率 90.8% 対 81.6%）、VocalSet の
男声では **+12 が +7 より良い**（明るさで 145 Hz 対 332 Hz）。**固定の定数で両方を賄えません。**
出力の明るさは入力 F0 に強く従うので、**source と target の F0 差から決めるほうが筋**です
（**未実装**。決めるには target を複数にした測定が要ります）。

#### 私の誤りを 2 つ記録します

1. **明るさに 2 つ目の定義を作ってしまいました。** 窓ごとの centroid の中央値・**振幅**重みで
   測ると **4229 Hz** になり、文書の 1160 Hz 台と食い違いました。repo の
   `tools/audio_metrics.band_profile`（**power** 重み、エネルギーが中央値以上のフレームだけ）
   で測り直すと **1177 Hz** で一致しました。**同じ量に別の定義を持ち込まないこと。**
2. **事前登録に「男声 10 本」と書きましたが、数える前でした**（実際は 11 本）。

### ボコーダーの内訳（2026-09-18 実測。M6 の起動判断の材料）

**確認済み。** 一次データは `out/m5/_m6/vocoder_profile.json`、合成入力で
`checkpoints/nhv_v3_1.onnx` を onnxruntime（CPU）に通したものです。**品質の話ではありません。**

| 見たもの | 結果 |
|---|---|
| **op 別の kernel 時間** | **DFT 42.9%**、Mul 14.0%、Sub 9.4%、Cast 7.5%、Floor 5.1%、Cos 4.9% |
| 重いノード | `node__to_copy_3` 7.4% / `node_sub_75` 6.5% / `node__fft_c2c_1` 6.1% / `node__fft_c2c_3` 5.7% / `node__fft_r2c_4` 5.3% |
| 入力長 | RTF は 5 / 10 / 20 秒で **0.505 / 0.482 / 0.492**。**長さに比例し、固定オーバーヘッドは小さい** |
| intra_op スレッド | 1 / 2 / 4 / 8 で RTF **0.598 / 0.540 / 0.548 / 0.453**。**8 倍にして 1.32 倍**しか速くならない |

**律速は FFT です。** 「acoustic を速くしても end-to-end は動かない」という既知の結論に、
**「ボコーダー側の律速は ONNX Runtime の DFT 実装である」**が加わります。

**次の一歩（未実施）:** 同じ計算を **torch.fft** で回して比べる。**依存を増やさずに測れます**
（`onnxruntime-gpu` を入れる判断は要りません）。ここで差が出ないなら、M6 は acoustic 側の
工夫では届かないことになります。

**注意:** ここの RTF は**この機種・合成入力・onnxruntime CPU** の値で、`tools/rtf.py` が
実音声で出した 0.355（CPU 合計の内訳）とは条件が違います。**混ぜないこと。**

### P0-2 低音域の実測（仮説の検証）

**目的:** 「YouTube 由来なら低音男声が入る」という仮説を、投入の前に検証する。

**設計:** mix（MP3、1 曲あたり約 5 MB）を shard をまたいで無作為に選び、RMVPE で F0 を測る。
**RMVPE は polyphonic 前提の抽出器**なので mix で測れる（論文題名が "in Polyphonic Music"）。
vocal-only（1 曲 35 MB）より **7 倍安い**。

**内部対照を先に置く:** 同一曲（両リポジトリに同じ動画 ID がある）で mix と vocal-only の F0 を
比べ、**中央値の差が 1 半音未満**であることを確かめる。ここが合わなければ mix での測定は使わない。

**指標:** C3（131.0 Hz）未満の**滞在率**（`preprocess/svc/coverage.py` の `pitch_band_seconds`、
edges = 131 / 262 / 523 Hz）。既存素材の最大は夏目悠李の **3.6%**。

**判定規則（この節を書いた後に測る）:**

1. **合格**: C3 未満の滞在率の**中央値が 3.6% を超える**、**かつ**曲単位で 3.6% を超えるものが
   **25% 以上**ある。中央値だけで決めない（clip 単位の振れ幅が大きいという既知の壊れ方）。
2. **不合格**: 上を満たさない → **1,000 h の投入は保留**。P1 は起動しない。
3. **測定無効**: 内部対照が不一致（同一曲で F0 中央値が 1 半音以上ずれる）→ vocal-only で測り直す。

**予測（外れたら残す）:** **合格**と予測する。utaite と official に男性歌手が多いため。
**ただし自信は低い** —— 既に測った 1 本（`--0fvYUtDas`、男性歌い手）は **0.5%** で、
夏目悠李の 3.6% より**少なかった**。

### P0-3 分離品質（上限が壊れないか）

**目的:** 分離 stem を ground-truth mel にしたとき、**上限（`*_vocoder_only.wav`）が既存素材と
同じ水準か**を測る。**帯域では検知できない**軸（伴奏 leakage・位相・残響）をここで見る。

**設計:** [`tools/nhv_indist.py`](../tools/nhv_indist.py) に任意のセットを足す口を付け（TDD）、
vocal-only を既存 5 コーパスと並べる。**条件は 7b 節と同一**にする: 12 clip・各 6 秒・seed 0・
有声率 0.3 未満は除外・`checkpoints/nhv_v3_1.onnx`。

**指標:** 原音 mel と再合成 mel の **L1 平均**（7b 節と同じ）。

**判定規則（この節を書いた後に測る）:**

1. **合格**: mel L1 平均が **0.4056 以下**。この閾値は**既存コーパス間のばらつきの実測**から
   立てた —— 既知 4 コーパスどうしの最大差が **+16.9%**（夏目 0.2969 対 リツ 0.3470）なので、
   最大値 0.3470 にその差を許す（0.3470 × 1.169）。**恣意的な「20%」ではなく、
   ノイズの実測に対して立てる。**
2. **不合格**: 超えた場合 → 上限が既存素材と別物になるので、**この素材で測った「上限との差」は
   既存の数値と比べられない**。base に入れるなら評価系統を分ける。
3. 併せて Mann-Whitney U で既知 5 コーパスと比べ、p も記録する（7b 節と同じ検定）。

**予測（外れたら残す）:** **合格**と予測する。分離の劣化は位相に強く出て mel L1 には出にくい
ため。**外れた場合は「mel L1 では分離アーティファクトを検知できない」という別の学びになり、
その時は指標を足さずに聴取へ回す。**

### P0-4 取り込みの実装（TDD）

**目的:** loader のデータ契約を満たす形にする。**分岐（P0-2 / P0-3 の結果）に関係なく要る。**

**ゴール:**

1. `channel_id` → 話者ディレクトリの割り当て。**`dataset_category == "cover"` のみ**を話者として
   扱う（`official` には `Warner Music Japan` のような複数アーティストの channel が実在する）。
2. `title` の照合による cover の畳み込み。曲名は **casefold してから記号を畳む**既存の規約に
   合わせる（崩すと曲単位 split が効かない）。
   **登録時は「重複の除去」と書いたが、実装で「同じ曲名へ畳む」に変えた（2026-09-19）。**
   同じ曲を別の歌手が歌ったものは学習素材として有効なので、**捨てずに split を揃える**ほうが
   正しい。判定規則には影響しない（P0-2 / P0-3 の合否は動かない）。
3. `min_bandwidth_hz` を **mel の上位 bin の中心（15,540 Hz）**から決める。16,000 Hz のままだと
   実測で **92%** が `band_limited` で弾かれるのに、**mel では 1 bin も失われない**。

**完了条件:** 失敗するテストを先に書き、通す。**合成 fixture のみ**で、重いモデルもネットワークも
使わない（`test_svc_preprocess` の方針）。

**結果（2026-09-19）: 1 と 3 は解決。2 は「解決していない」と記録する。**
実装は `preprocess/svc/sidecar.py`、テストは `test_svc_preprocess` に 20 件。

**自作の文字列だけで通したテストは、実データで落ちました。** 実タイトル 13 本を通したところ、

- 想定していた `歌わせて` ではなく **`うたった`**（ひらがな）が実際の表記だった。
- **`Artist - Song` を区切り記号で割ると、アーティスト名が曲名になる**
  （`Misumi - アンダードッグ feat.flower` が `misumi` に潰れた）。**その歌手の全曲が 1 曲へ
  潰れる**ので、GTSinger で 1,723 ファイルが潰れたのと同じ壊れ方をする。ハイフンを区切りから
  外し、`feat. <歌手>` を落とすようにした。

**残る限界（確認済み）: cover の自動グルーピングは解決していません。** 修正後も
`ピノキオピー - ラヴィット` / `misumi - アンダードッグ` / `claris_ケアレス` のように
**アーティスト名が曲名に残る**ため、同じ曲の bare な cover（`ラヴィット／歌ってみた`）とは
**別の曲名になります**。**過剰に畳むより安全な方向**（畳まないだけ）ですが、
**曲単位 split の leakage は残ります**。

**緩和策（P1 の前にやること）:** 学習素材は `cover` だけなので、`Artist - Song` 型の題名が
多い `official` は最初から入りません。それでも実測では **cover 4 本中 2 本**が
アーティスト名を含んでいたので、**全メタデータに `duplicate_groups()` を掛けて目視**し、
必要なら「同じ曲名が複数 channel に出るものを除外」する。**自動では閉じません。**

### P0-3 の結果（2026-09-19 実測）: **不合格。上限が既存素材と別物になります**

**測り方は登録どおり。** 7b 節と同一条件（12 clip・各 6 秒・seed 0・有声率 0.3 未満は除外・
`checkpoints/nhv_v3_1.onnx`）で、**既存 5 コーパスと同じ run に並べて**測りました
（ボコーダーの出力は run ごとに変わるので、同じ run に入れる意味があります）。
素材は vocal-only の shard 先頭から取った 12 曲、生データは `.m0data/p0/nhv_indist/`。

| set | NHVSing 学習 | clips | mel L1 平均 | 中央値 | 標準偏差 | F0 半音 | V/UV |
|---|---|---:|---:|---:|---:|---:|---:|
| 波音リツ | あり | 12 | 0.3332 | 0.3337 | 0.037 | 0.0193 | 0.9868 |
| 夏目悠李 | あり | 12 | 0.2951 | 0.3064 | 0.041 | 0.0230 | 0.9725 |
| 御丹宮くるみ | あり | 12 | 0.3102 | 0.3111 | 0.026 | 0.0104 | 0.9926 |
| VocalSet | あり | 12 | 0.2929 | 0.3018 | 0.031 | 0.0141 | 0.9898 |
| GTSinger 日本語 | なし | 12 | 0.3371 | 0.3263 | 0.046 | 0.0139 | 0.9894 |
| **tts-dataset 分離ボーカル** | なし | 12 | **0.5279** | 0.5319 | **0.122** | **0.0387** | **0.9485** |

**判定は不合格です。** 登録した合格線は **0.4056**（既存コーパス間の最大差 +16.9% を
最大値 0.3470 に許した値）で、実測は **0.5279**。既存 5 セットの範囲（0.2929〜0.3371）の
**+56.6%** 外側です。

**clip 単位でも明確です。** Mann-Whitney U（登録どおり）で **U = 663.0、p = 0.000002**。
**既存 60 clip の最大（0.4259）を、tts の 12 clip 中 10 本が上回りました。**

**予測は外れました（登録どおり残します）。** 「分離の劣化は位相に強く出るので mel L1 には
出にくい」と予測しましたが、**mel L1 にはっきり出ました**。F0 半音誤差（0.0387、他は
0.0104〜0.0230）と V/UV 一致率（0.9485、他は 0.9725〜0.9926）も同じ向きです。
**登録した「指標を足さずに聴取へ回す」は、外れ方が逆だったので発動しません** ――
検知できなかったのではなく、検知できました。

**読める範囲（重要）:** この測定が言えるのは「**この素材の GT mel は NHVSing にとって
再合成が難しい = 上限が既存素材と別物**」までです。**原因を分離アーティファクトに帰属
できません** —— tts の 12 本は**マスタリング済みの配信音源をボーカル分離したもの**で、
しかも**曲まるごと**です。既存 5 セットは**スタジオ収録の DB**なので、
**分離・マスタリング・素材の種類が全部同時に違います。**

**したがって:** この素材で測った「上限との差」は、**既存の数値（M4 / M5 の +12.7 点など）と
並べられません。** 使うなら評価系統を分ける必要があります。

## 13. P1: 1,000 時間素材での base 事前学習（2026-09-20 **測定の前に登録**）

**起動の根拠は利用者の判断**です（12 節の「中止条件の解除」）。**品質の仮説ではありません** ――
低音域は入っていないと測れており、期待できるのは**話者数と曲の多様性**だけです。

### この素材は既存 base と形が違う（確認済み）

**1 channel あたり 1.1 曲**でした（標本 75 曲に 68 channel）。全体では **約 14,000 話者 ×
1 曲（約 4 分）**という「**広く浅い**」構成になります。

| | 現 base（m3_base） | この素材（cover 全部なら） |
|---|---:|---:|
| 話者数 | 23 | **約 4,000〜5,000**（cover が約 30%） |
| 1 話者あたり | 約 0.75 h | **約 0.07 h（4 分）** |
| 合計 | 約 18 h | 約 300 h |

**これは既存方針（「base では総時間より話者の多様性が効く」）を極端まで振ったもの**です。
**未検証の領域**で、**1 話者 4 分で話者条件（`spk_bank`）が学習できるかは分かりません。**

### 規模の制約（見積もり）

**shard は約 1.6 GB / audio-hour** です（実測。256 次元 content + mel + 768 次元 cache）。

| 素材量 | shard 容量 | 判断 |
|---:|---:|---|
| 1,000 h（全部） | **1.6 TB** | **不可** |
| 300 h（cover 全部） | 480 GB | 現実的でない（M3 は disk 150 GB で 18 h） |
| **50〜80 h** | **80〜128 GB** | **最初の run はここ** |

**決定: 最初の run は `cover` から話者を無作為に選び、1 話者 1 曲、50〜80 h（= 750〜1,200 話者）。**
現 base の**話者数 33〜52 倍、時間 3〜4 倍**です。`--max-hours` は使いません
（**全員が 1 曲 4 分なので揃っている**）。

### 設計

- **`dataset_category == "cover"` のみ**を使う。`official` は channel = 話者にならない
  （`Warner Music Japan` が実在）。`diverse` も話者として扱わない。
- 話者 id は `channel_id`（`preprocess/svc/sidecar.py` の `speaker_key()`）。
- 曲名は `song_key()`。**cover の自動グルーピングは未解決**なので、**投入前に
  `duplicate_groups()` を全メタデータへ掛けて目視**する。
- 帯域の足切りは `min_bandwidth_for_mel()`（既定 mel で 15,540 Hz）。**16,000 Hz のままだと
  92% が弾かれる。**
- `eval_items: 1` と大きい `eval_interval`。**話者数が 3 桁になるので、eval は話者の
  サブセットに限る必要があります**（話者ごとに eval を作る実装なので、**未実装なら eval を切る**）。

### 指標と、なぜそれを選ぶか

**評価 test set は従来どおり**（リツの hold-out 6 clip と VocalSet の未知 source）。
**上限は既存のものを `--ceiling-from` で使い回す**ので、**現 base の数値とそのまま比べられます**
（12 節の訂正）。

| 指標 | 理由 |
|---|---|
| 明瞭度（CER の上限との差・**差の中央値**） | 唯一「動く軸」が分かっている指標。**対応のある検定を併記** |
| 話者類似度（回復率） | 話者数 40 倍の効果が最も出るとしたらここ |
| 内容 cos（未知 source） | 劣化の検出（M4 の規則を流用） |
| 明るさ（上限比・**絶対値**） | 学習素材の mel 分布が動いた影響を見る。**符号つき平均では見ない** |

### 判定規則（**この節を書いた後に測る**）

1. **改善と認める**: 明瞭度の**差の中央値**が現 base より良く、**かつ clip 単位の対応のある
   検定で有意**（p < 0.05）。**中央値だけでは認めません**（振れ幅が最大 73.6 点あった実測）。
2. **悪化と認める**: 内容 cos が現 base から **0.02 を超えて落ちる**、または明るさの
   |上限比 − 1| が現 base より悪化。どちらかが起きたら**この素材は base に向かない**と結論する。
3. **変わらない**: 1 も 2 も起きない場合。**「話者数を 40 倍にしても動かない」という結論**として
   記録し、**追加投入（80 h → 300 h）はしない**。

### 予測（外れたら残す）

**「変わらない」と予測します。** 実測で話者の既知性・base の学習量・step 数・GAN のいずれも
明瞭度を動かさず、動いたのは「その曲を学習で見たか」だけでした。**話者数はその軸ではありません。**
**ただし話者類似度は上がる可能性があります**（話者条件の学習量が増えるため）。

直接の証拠が付きます。** そのときは 300 h への拡大を検討します。
